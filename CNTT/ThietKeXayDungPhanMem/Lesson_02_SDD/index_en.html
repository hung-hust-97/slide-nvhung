WHAT IS SDD?

Definition

SDD is a comprehensive document describing the architecture, design and functionality of a software system. [IEEE 1016]

Purpose

  • Serves as a guide for developers, testers and stakeholders
  • Provides clear understanding of the software structure and how it works
  • Bridge between requirements (SRS) and source code

Role in SDLC (Software Development Life Cycle)

SDLC — Software Development Life Cycle — the process from idea to finished product:

1

Requirements (SRS)

Gather and analyze requirements

2

Design (SDD) ← We are here

Design architecture, modules, database, interfaces

3

Implementation → Testing → Deployment

Write code, test, deploy

✨ MODERN TRENDS

In Agile, SDD is continuously updated each Sprint. Many teams use Confluence, Notion or wiki instead of Word. [Atlassian]

BENEFIT 2: CLEAR COMMUNICATION & SHARED UNDERSTANDING

💬 Ensuring everyone understands the system the same way

  • Consistent code across team members, fewer misunderstandings
  • Stakeholders (clients, managers) understand the system without reading code
  • New members onboard quickly by reading SDD instead of asking colleagues
  • Reduces dependency on one person's "knowledge in their head" — avoids bus factor = 1

Real-world Examples — Google: Google duy trì hệ thống tài liệu thiết kế nội bộ gọi là "Design Docs". Mọi dự án lớn bắt buộc viết design doc trước khi code. BENEFIT 4: EASY MAINTENANCE & SCALABILITY

🔧 Maintenance

  • Fast debugging: SDD is a map to find root causes — knowing which module is responsible
  • Safe changes: Clearly know which components are affected when modifying code (impact analysis)
  • Reduce "spaghetti code": Clear design prevents uncontrolled code growth

📈 Scalability

  • Modular design allows adding new modules without breaking existing ones
  • Good architecture enables horizontal scaling as users grow

Ví dụ — Netflix: Ban đầu Netflix là 1 ứng dụng monolithic. Khi người dùng tăng lên hàng trăm triệu, họ dùng SDD để chuyển đổi sang microservices (hơn 1.000 services). Nhờ tài liệu thiết kế rõ ràng, mỗi đội có thể deploy hàng nghìn lần/ngày mà không ảnh hưởng đội khác. [Netflix Tech Blog]

Ví dụ — Grab: Kiến trúc SDD giúp Grab mở rộng từ taxi sang food, payment, logistics — mỗi "vertical" là module riêng, phát triển độc lập nhờ API contracts rõ ràng trong SDD. [Grab Engineering]

BENEFIT 5: RISK REDUCTION & COST SAVINGS

⚠️ Risk Mitigation

  • SDD forces the team to assess technical risks before coding: dependencies, bottlenecks, single points of failure
  • Analyze feasibility of architecture before investing coding time
  • Theo Standish Group CHAOS Report, lack of design/documentation is a leading cause of ~30% IT project failures [Standish Group]

💰 Cost Savings

  • Fixing errors at design costs 1x, at code 6.5x, at testing 15x, at production 100x [IBM Systems Sciences]
  • Reduce rework: correct design from the start → less redo
  • Reuse: good design can be reused for other projects

Ví dụ — Healthcare.gov: Thất bại $2 tỷ USD do 55 nhà thầu xây module không tương thích — thiếu SDD kiến trúc tổng thể. [Wikipedia]

HLD — WHEN NEEDED & CREATION PROCESS

When to write HLD?

  • Projects with multiple teams or multiple contractors developing simultaneously
  • Systems integrating multiple services (microservices, 3rd party APIs)
  • Need stakeholder approval before coding (clients, managers, architects)
  • Projects with legal compliance requirements (finance, healthcare, defense)
  • Systems needing future scalability (scalability planning)

Who creates HLD?

  • Solution Architect or Tech Lead — not developers
  • Reviewed by: PM, CTO, stakeholders, security team

HLD Creation Process (5 steps):

1

Gather requirements

Read SRS, meet with stakeholders, define scope

2

Define architecture

Choose pattern (layered, microservices...), draw architecture diagram

3

Identify components

List modules, APIs, databases, 3rd party integrations

4

Draw diagrams

Architecture diagram, data flow, deployment diagram

5

Review & approve

Stakeholders review, feedback, update, sign-off

2. LOW-LEVEL DESIGN DOCUMENT (LLD)

LLD describes low-level detailed requirements of subcomponents and submodules — for developers and testers. [Software Dominos]

LLD contents include:

  • Details via flowcharts, pseudocode, flow diagrams
  • Specifically identifies source code files, data model tables, functions to modify
  • Helps testers understand scope of changes → directs testing effort
  • Includes exception handling and negative scenarios
  • Class diagrams detailed with attributes & methods
  • Sequence diagrams for each processing flow

2. LLD EXAMPLE: USER AUTHENTICATION MODULE

Detailed LLD example for Authentication module — describing pseudocode, processing flow, and exception handling at implementation level. [Software Dominos]

Class: AuthService (Pseudocode)

class AuthService:
  - userRepo: UserRepository
  - jwtService: JWTService
  - emailService: EmailService
  - bcrypt: BCryptEncoder

  + login(email, password): JWT
    1. Find user by email
    2. Compare password (BCrypt)
    3. Create JWT token (RS256, 24h)
    4. Return token

  + resetPassword(email): void
    1. Generate reset token (UUID)
    2. Save token + expiry (1h)
    3. Send email with reset link

Sequence: Login Flow

User → UI: Enter email + password
UI → AuthController: POST /api/auth/login
AuthController → AuthService: login(email, pwd)
AuthService → UserRepo: findByEmail(email)
UserRepo → DB: SELECT * WHERE email=?
AuthService → BCrypt: matches(pwd, hash)?
  If wrong → throw 401 Unauthorized
AuthService → JWTService: generateToken(user)
AuthController → UI: 200 OK + {token, user}
UI → User: Redirect to Dashboard

Exception Handling:

  • Email does not exist → 404 "User not found"
  • Wrong password → 401 "Invalid credentials"
  • Account locked → 403 "Account locked"
  • More than 5 failed attempts → Lock for 30 minutes

3. ARCHITECTURAL DESIGN DOCUMENT

Describes the overall structure of the software system — how components are organized, communicate and deploy. This is the most important document helping the team understand the "big picture" before coding. [Wikipedia]

Content chính của ADD:

  • Architectural Views — describes the system from multiple perspectives (Kruchten's 4+1 model) [4+1 View]
  • Quality Attributes — non-functional requirements: scalability, availability, performance, security
  • Architectural Decisions (ADRs) — record decisions + reasons + trade-offs [Michael Nygard]
  • Technology Stack — language, framework, database, cloud services
  • Constraints — constraints on technology, budget, legal, team skills

4+1 View Model (Kruchten):

ViewDescription
LogicalModules, classes, packages — logical structure
ProcessConcurrency, threads, communication
DevelopmentSource code organization, layers, libraries
PhysicalDeployment: servers, containers, network
+1 ScenariosUse cases to validate architecture
✨ MODERN TRENDS

Architecture Decision Records (ADRs) are widely adopted — each architectural decision is recorded as a concise file in the repo, helping newcomers understand "why" the system was designed that way. [Cognitect]

IEEE 1016 STANDARD & DESIGN RATIONALE

IEEE 1016-2009 — International Standard for SDD

Definition cách tổ chức tài liệu thiết kế theo 12 design viewpoints (góc nhìn thiết kế), mỗi viewpoint mô tả hệ thống từ một khía cạnh khác nhau: [IEEE 1016]

ViewpointDescription
ContextSystem context, actors, external systems
CompositionComponent structure and relationships
LogicalBusiness logic, class diagrams, business rules
InterfaceInterfaces between modules (APIs, contracts)
InteractionSequence diagrams, interaction flows between components
InformationData model (ERD, data flow)
+6 othersAlgorithm, State, Dependency, Structure, Resource, Physical

The 9 design aspects in these slides cover most IEEE 1016 viewpoints, grouped for easier understanding in practice.

Design Rationale

Required by IEEE 1016 and NASA — each design decision must record why that solution was chosen, not just describe "what": [NASA SwDD]

  • Alternatives: options considered (at least 2-3 options)
  • Decision: reason for choosing the current option — based on what criteria (cost, performance, complexity)
  • Constraints: constraints on technology, budget, timeline, team skills
  • Assumptions: assumptions that are true at the time of decision
  • Trade-offs: accepted risks and limitations, mitigation approaches

VD: "Chose JWT over Session because we need stateless for microservices, easy horizontal scaling. Trade-off: token cannot be immediately revoked — mitigated by short expiry (15 minutes) + refresh token."
