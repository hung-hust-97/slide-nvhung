TỔNG QUAN CÁC MẪU KIẾN TRÚC

Thứ tự trình bày từ đơn giản → phức tạp, phản ánh tiến hóa kiến trúc phần mềm:

PatternĐặc điểm chínhPhù hợp cho
1. MonolithicToàn bộ ứng dụng là 1 đơn vị, tất cả components kết nối chặt chẽStartup, MVP, team nhỏ
2. Layered (N-Tier)Chia ứng dụng thành các tầng (Presentation → Business → Data), mỗi tầng có trách nhiệm riêngWeb app, enterprise (ERP, CRM)

5. Event-DrivenLuồng hệ thống điều khiển bởi events, giao tiếp bất đồng bộ qua message brokerReal-time, IoT, data pipeline

MONOLITHIC ARCHITECTURE — TỔNG QUAN

Toàn bộ ứng dụng được xây dựng như một đơn vị duy nhất. Tất cả thành phần (UI, business logic, data access) được kết nối chặt chẽ và hoạt động như một đơn vị triển khai. [Wikipedia]

VD: Ứng dụng Java Spring Boot đóng gói thành 1 file .jar — chứa tất cả controllers, services, repositories. Browser gửi HTTP request → 1 application xử lý tất cả → trả response.

Đặc điểmMô tả
Unified CodebaseToàn bộ ứng dụng nằm trong 1 codebase, phát triển ban đầu dễ dàng
Tight CouplingTất cả module tích hợp chặt, phụ thuộc lẫn nhau
Single DeploymentĐóng gói và deploy 1 lần (1 file .jar/.war/.exe)
Shared DatabaseSử dụng 1 database tập trung cho tất cả module
Homogeneous StackToàn bộ ứng dụng dùng 1 tech stack/framework

MONOLITHIC — ƯU & NHƯỢC ĐIỂM

Ưu điểm:

  • Simplified Development — 1 project, 1 IDE, dễ bắt đầu
  • High Performance — giao tiếp trực tiếp giữa components (in-process calls), không cần network
  • Easier Debugging — trace lỗi trong 1 codebase
  • Simple Deployment — deploy 1 file duy nhất
  • Simple Testing — test end-to-end dễ dàng

Nhược điểm:

  • Scalability kém — phải scale toàn bộ ứng dụng
  • Deployment Bottlenecks — thay đổi nhỏ cũng phải deploy lại toàn bộ
  • Limited Fault Isolation — lỗi 1 module có thể crash toàn app
  • Not Cloud-Native Friendly — khó tận dụng container orchestration
  • Codebase phình to — khó hiểu, khó maintain theo thời gian
✨ XU HƯỚNG HIỆN ĐẠI

Shopify vẫn dùng Modular Monolith — monolithic nhưng chia thành bounded contexts rõ ràng. Đây là bước trung gian trước khi chuyển sang microservices. [Shopify Engineering]

Khi nào monolithic là đủ?

  • Team ≤ 5 người
  • MVP hoặc prototype
  • Domain đơn giản, ít module
  • Không cần scale từng phần
  • Deadline gấp, cần ship nhanh

LAYERED ARCHITECTURE — TỔNG QUAN

Mô hình thiết kế chia ứng dụng thành nhiều tầng (layers), mỗi tầng có vai trò và trách nhiệm cụ thể. Đây là kiến trúc phổ biến nhất cho ứng dụng web và enterprise. [Wikipedia]

1

Presentation Layer

Giao diện người dùng (UI), API Gateway. Xử lý input và hiển thị dữ liệu.

2

Application Layer

Điều phối luồng logic nghiệp vụ. Chứa Services, Use Cases.

3

Domain / Business Logic Layer

Xử lý tập trung các quy tắc nghiệp vụ. Chứa Entities, Business Rules.

4

Data Layer

Quản lý dữ liệu: Repositories, DAO. Lưu trữ và truy xuất từ database.

Nguyên tắc: Mỗi tầng chỉ gọi tầng ngay bên dưới, không được "nhảy cóc" qua tầng.

12 ThS. Nguyễn Việt Hưng - Trường Đại học CMC

PRESENTATION LAYER

Vai trò: Tương tác trực tiếp với người dùng cuối.

Thành phần:

  • User Interface (UI) — Angular components, HTML/CSS
  • API Gateway — điểm vào duy nhất cho client
  • Controllers — nhận HTTP request, trả response

Chức năng:

  • Xử lý thông tin đầu vào từ người dùng (click, nhập liệu)
  • Hiển thị dữ liệu cho người dùng
  • Validation phía client (format email, required fields)
  • Routing, navigation

Ví dụ với Angular:

src/app/
  components/
    login/
      login.component.ts
      login.component.html
    dashboard/
      dashboard.component.ts
  services/
    auth.service.ts
    api.service.ts
  guards/
    auth.guard.ts

Presentation Layer chỉ gọi Application Layer thông qua HTTP APIs, không truy cập database trực tiếp.

APPLICATION & DOMAIN LAYER

Application Layer

Vai trò: Điều phối luồng logic nghiệp vụ.

  • Services — orchestrate business operations
  • Use Cases — xử lý từng tác vụ cụ thể
  • DTOs — Data Transfer Objects giữa các tầng

Ví dụ với Java Spring Boot:

@Service
public class CourseService {
  @Autowired
  private CourseRepository repo;

  public CourseDTO getCourse(Long id) {
    Course c = repo.findById(id)
      .orElseThrow();
    return mapper.toDTO(c);
  }
}

Domain / Business Logic Layer

Vai trò: Xử lý tập trung các quy tắc nghiệp vụ.

  • Entities — đối tượng nghiệp vụ (User, Course, Order)
  • Business Rules — quy tắc (giá ≥ 0, đăng ký ≤ max)
  • Value Objects — Email, Money, Address
  • Domain Events — sự kiện nghiệp vụ
@Entity
public class Course {
  @Id @GeneratedValue
  private Long id;
  private String title;
  private BigDecimal price;

  public void enroll(User user) {
    if (students.size() >= maxCapacity)
      throw new FullException();
    students.add(user);
  }
}

DATA LAYER

Vai trò: Quản lý dữ liệu của hệ thống — lưu trữ và truy xuất từ database hoặc các nguồn khác.

Thành phần:

  • Repositories — interface truy cập dữ liệu
  • DAO (Data Access Objects) — triển khai cụ thể
  • ORM Mapping — ánh xạ Entity ↔ Table (JPA/Hibernate)
  • Database Migrations — Flyway, Liquibase

Ví dụ Repository (Spring Data JPA):

public interface CourseRepository
    extends JpaRepository<Course, Long> {

  List<Course> findByCategory(String cat);

  @Query("SELECT c FROM Course c
    WHERE c.price <= :max")
  List<Course> findAffordable(BigDecimal max);
}

    CourseService.java
  model/          ← Domain
    Course.java
    User.java
  repository/     ← Data
    CourseRepository.java
  dto/
    CourseDTO.java
  config/
    SecurityConfig.java

Mỗi package tương ứng với 1 layer — giúp tổ chức code rõ ràng theo kiến trúc phân lớp.

LAYERED ARCHITECTURE — ƯU & NHƯỢC ĐIỂM

Ưu điểm:

  • Bảo trì dễ — thay đổi 1 tầng không ảnh hưởng tầng khác
  • Phân tách rõ ràng — mỗi tầng có trách nhiệm riêng (Separation of Concerns)
  • Dễ test — mock từng tầng để unit test
  • Mở rộng — thêm tầng hoặc thay đổi implementation
  • Team collaboration — FE team làm Presentation, BE team làm Business + Data

Nhược điểm:

  • Performance overhead — request phải đi qua nhiều tầng
  • Phức tạp hơn — nhiều tầng = nhiều code boilerplate
  • Khó tối ưu — luồng dữ liệu bắt buộc đi qua từng tầng
  • Tight coupling giữa các tầng — nếu thiết kế không tốt
✨ XU HƯỚNG HIỆN ĐẠI

Java Spring Boot + Angular là ví dụ điển hình của Layered Architecture: Angular (Presentation) → Spring Controllers (Application) → Services (Domain) → JPA Repositories (Data).

MVC PATTERN — TỔNG QUAN

Model-View-Controller (MVC) là pattern tách ứng dụng thành 3 thành phần độc lập, giúp phân tách logic, giao diện và điều khiển. Đây là biến thể phổ biến nhất của Layered Architecture cho web app. [Wikipedia]

3 thành phần:

  • Model — Dữ liệu và business logic (Entity, Service, Repository)
  • View — Giao diện người dùng (HTML/CSS, Angular templates)
  • Controller — Điều phối: nhận request từ View, gọi Model, trả kết quả về View

Luồng hoạt động:

User → Controller (nhận request) → Model (xử lý data) → View (hiển thị) → User

MVC Pattern — luồng tương tác giữa Model, View, Controller

MVC — ƯU & NHƯỢC ĐIỂM

Ưu điểm:

  • Separation of Concerns — tách rõ logic, giao diện, điều khiển
  • Parallel Development — FE và BE phát triển song song
  • Reusable Models — Model dùng chung cho nhiều Views
  • Testable — unit test Controller và Model riêng biệt
  • Framework support — Spring MVC, Angular, .NET MVC đều built-in

Nhược điểm:

  • Learning curve — cần hiểu rõ luồng MVC
  • Boilerplate code — nhiều file cho 1 tính năng (Entity, DTO, Service, Controller, Component, Template)
  • Controller phình to — nếu không tách Service, Controller dễ trở thành "God class"
  • Phức tạp với UI đơn giản — overhead cho ứng dụng nhỏ

MICROSERVICES ARCHITECTURE — TỔNG QUAN

Ứng dụng được phát triển như một tập hợp các service nhỏ, độc lập và loosely coupled. Mỗi service chịu trách nhiệm cho một khả năng nghiệp vụ cụ thể và có thể phát triển, triển khai, scale độc lập. [Martin Fowler]

VD: Ứng dụng e-commerce gồm: UserService, ProductService, OrderService, PaymentService, NotificationService — mỗi service có database riêng, deploy riêng, có thể viết bằng ngôn ngữ khác nhau.

Independence

Mỗi service là đơn vị độc lập — develop, deploy, maintain riêng

Bounded Context

Mỗi service chịu trách nhiệm 1 chức năng nghiệp vụ cụ thể

Decentralized Data

Mỗi service quản lý database riêng — data isolation

APIs for Communication

Giao tiếp qua REST, gRPC, hoặc messaging (Kafka)

MICROSERVICES — ƯU & NHƯỢC ĐIỂM

Ưu điểm:

  • Scalability — scale từng service độc lập
  • Flexibility in Technology — dùng tech stack khác nhau
  • Faster Development — team nhỏ phát triển song song
  • Improved Fault Isolation — lỗi không lan rộng
  • Easier Maintenance — codebase nhỏ, dễ hiểu
  • Independent Deployment — deploy không cần downtime toàn hệ thống

Nhược điểm:

  • Increased Complexity — quản lý nhiều service
  • Communication Overhead — network calls giữa services
  • Data Consistency — khó duy trì consistency across services
  • Requires robust DevOps — CI/CD, monitoring, logging cho từng service
  • Testing phức tạp — integration test giữa nhiều services

EVENT-DRIVEN ARCHITECTURE (EDA) — TỔNG QUAN

Kiến trúc hướng sự kiện — luồng hoạt động được điều khiển bởi events. Tập trung vào việc sản xuất, phát hiện và phản ứng với các sự kiện. Khả năng thích ứng cao với hệ thống bất đồng bộ, phân tán và real-time. [Wikipedia]

Event Producer

Tạo ra events khi có thay đổi trạng thái (VD: đơn hàng được tạo, sensor kích hoạt). Publish event đến Event Broker.

Event Broker

Trung tâm quản lý events — nhận từ Producer, phân phối đến Consumer. VD: Apache Kafka, RabbitMQ, Amazon SNS/SQS.

Event Consumer

Đăng ký nhận loại event quan tâm. Thực hiện hành động tương ứng (gửi notification, xử lý giao dịch).

VD: User đặt hàng → OrderService publish event "OrderCreated" → PaymentService xử lý thanh toán → NotificationService gửi email → InventoryService cập nhật kho.

EVENT PRODUCERS & CONSUMERS

Producers (Nhà sản xuất):

  • Tạo ra events khi có sự kiện hoặc thay đổi trạng thái
  • VD: đơn hàng được đặt, cảm biến kích hoạt, user đăng ký
  • Publish events đến Event Broker
  • Không cần biết ai sẽ nhận event (decoupled)

Consumers (Người tiêu thụ):

  • Đăng ký (subscribe) các loại event quan tâm
  • Lắng nghe (consume) events từ Event Broker
  • Thực hiện hành động tương ứng
  • VD: gửi notification, xử lý thanh toán, cập nhật cache

Event Broker (Trung gian):

Trung tâm quản lý events, đảm bảo events được phân phối đến tất cả consumers đã đăng ký.

BrokerĐặc điểm
Apache KafkaHigh throughput, durable, distributed log. Phù hợp data pipeline lớn
RabbitMQFlexible routing, nhiều protocol (AMQP). Phù hợp task queue
Amazon SNS/SQSManaged service, dễ scale. Phù hợp cloud-native

EDA — ƯU & NHƯỢC ĐIỂM

Ưu điểm:

  • Asynchronous Communication — không cần chờ response
  • Loose Coupling — services không phụ thuộc trực tiếp
  • Scalability — scale từng consumer độc lập
  • Flexibility — thêm consumer mới không ảnh hưởng hệ thống
  • Real-Time Processing — xử lý ngay khi event xảy ra

Nhược điểm:

  • Increased Complexity — quản lý luồng event phức tạp
  • Debugging khó — trace luồng bất đồng bộ
  • Event Ordering — khó đảm bảo thứ tự events
  • Requires robust middleware — cần Kafka/RabbitMQ ổn định
  • Eventual Consistency — dữ liệu không nhất quán tức thì

TIẾN HÓA KIẾN TRÚC PHẦN MỀM

Kiến trúc phần mềm không cố định — nó phát triển cùng với hệ thống. Nhiều tổ chức lớn đã trải qua quá trình tiến hóa sau:

1

Monolithic

Bắt đầu đơn giản, ship nhanh MVP. VD: Shopify, Netflix giai đoạn đầu

2

Modular Monolith

Chia monolith thành modules rõ ràng (bounded contexts), chuẩn bị cho tách service. VD: Shopify hiện tại

3

Microservices

Tách modules thành services độc lập khi cần scale. VD: Netflix, Uber, Amazon

4

Event-Driven + Microservices

Kết hợp async messaging cho real-time, loose coupling. VD: LinkedIn, fintech

✨ XU HƯỚNG HIỆN ĐẠI

Martin Fowler khuyên: "MonolithFirst" — bắt đầu với monolith, chỉ chuyển sang microservices khi thực sự cần. Premature decomposition tốn kém hơn monolith. [Martin Fowler]

HƯỚNG DẪN LỰA CHỌN KIẾN TRÚC

1

Team nhỏ (<5 người), MVP, deadline gấp?

→ Monolithic — đơn giản, nhanh, dễ debug

2

Web app enterprise, cần structure rõ ràng?

→ Layered Architecture — separation of concerns, dễ maintain, phù hợp Java Spring Boot + Angular

3

Cần real-time, async, data pipeline?

→ Event-Driven — Kafka/RabbitMQ, loose coupling, real-time processing

4

Hệ thống lớn, nhiều team, cần scale từng phần?

→ Microservices — independent deployment, polyglot, fault isolation

✨ XU HƯỚNG HIỆN ĐẠI

Nhiều tổ chức bắt đầu với Monolithic → Modular Monolith → Microservices (evolutionary architecture). Không nên dùng microservices từ đầu nếu team nhỏ và chưa hiểu rõ domain. [Martin Fowler]

CASE STUDY: TIẾN HÓA KIẾN TRÚC CỦA NETFLIX

Giai đoạn phát triển:

NămKiến trúcLý do chuyển đổi
2007Monolithic (Java)Ban đầu đủ dùng
2008DB corruption → 3 ngày downtimeSingle point of failure
2009-2012Migration to Cloud + MicroservicesScale cho 200+ quốc gia
2016+1000+ microservices trên AWSIndependent deployment, fault isolation

Quá trình chuyển đổi mất 7 năm — không phải overnight. [Netflix Tech Blog]

Bài học rút ra:

  • Bắt đầu monolithic khi chưa hiểu rõ domain
  • Chuyển sang microservices khi có nhu cầu thực sự (scale, team lớn)
  • Migration là quá trình dài, không phải rewrite
  • Cần DevOps maturity trước khi chuyển (CI/CD, monitoring, logging)
  • Chaos Engineering (Chaos Monkey) để test fault tolerance

Netflix open-source nhiều tools: Eureka (service discovery), Zuul (API gateway), Hystrix (circuit breaker) — được sử dụng rộng rãi trong hệ sinh thái Spring Cloud.
