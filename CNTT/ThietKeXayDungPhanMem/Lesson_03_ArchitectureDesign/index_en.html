REVIEW: SRS & IMPACT ON ARCHITECTURE

* SRS, User Stories, Use Cases were covered in detail in Lesson 02 (SDD). Here we focus on how they influence architecture decisions.

SRS ComponentContentImpact on Architecture
Functional RequirementsWhat the system must do — Use Cases, User StoriesDetermines which components are needed (modules, services)
Non-Functional RequirementsPerformance, security, scalability, availabilityDetermines patterns and infrastructure (monolithic vs microservices)
ConstraintsTechnology, budget, timeline, team sizeLimits choices (e.g., team of 3 → should not use microservices)
DependenciesThird-party APIs, legacy systems, external servicesDetermines integration patterns (API Gateway, message queue)

Principle: Functional requirements tell us what the system needs to do → identify components. Non-functional requirements tell us how the system must behave → determine architecture.

Select language, framework, database, infrastructure suitable for the chosen pattern

MONOLITHIC ARCHITECTURE — OVERVIEW

The entire application is built as a single unit. All components (UI, business logic, data access) are tightly coupled and operate as a single deployment unit. [Wikipedia]

Example: A Java Spring Boot application packaged as a single .jar file — containing all controllers, services, repositories. Browser sends HTTP request → 1 application handles everything → returns response.

CharacteristicDescription
Unified CodebaseThe entire application resides in 1 codebase, easy to start development
Tight CouplingAll modules are tightly integrated, dependent on each other
Single DeploymentPackaged and deployed at once (1 .jar/.war/.exe file)
Shared DatabaseUses 1 centralized database for all modules
Homogeneous StackThe entire application uses 1 tech stack/framework
9 MSc. Nguyen Viet Hung - CMC University

MONOLITHIC — ADVANTAGES & DISADVANTAGES

Advantages:

  • Simplified Development — 1 project, 1 IDE, easy to start
  • High Performance — direct communication between components (in-process calls), no network needed
  • Easier Debugging — trace errors within 1 codebase
  • Simple Deployment — deploy a single file
  • Simple Testing — easy end-to-end testing

Disadvantages:

  • Poor Scalability — must scale the entire application
  • Deployment Bottlenecks — even small changes require redeploying everything
  • Limited Fault Isolation — an error in 1 module can crash the entire app
  • Not Cloud-Native Friendly — hard to leverage container orchestration
  • Codebase bloat — hard to understand and maintain over time
✨ MODERN TRENDS

Shopify still uses a Modular Monolith — monolithic but divided into clear bounded contexts. This is an intermediate step before transitioning to microservices. [Shopify Engineering]

LAYERED ARCHITECTURE — OVERVIEW

A design model that divides the application into multiple layers, each layer having a specific role and responsibility. This is the most common architecture for web and enterprise applications. [Wikipedia]

1

Presentation Layer

User interface (UI), API Gateway. Handles input and displays data.

2

Application Layer

Orchestrates business logic flow. Contains Services, Use Cases.

3

Domain / Business Logic Layer

Centralized processing of business rules. Contains Entities, Business Rules.

4

Data Layer

Manages data: Repositories, DAO. Stores and retrieves from database.

Principle: Each layer only calls the layer directly below it, no "skipping" layers.

12 MSc. Nguyen Viet Hung - CMC University

PRESENTATION LAYER

Role: Directly interacts with the end user.

Components:

  • User Interface (UI) — Angular components, HTML/CSS
  • API Gateway — single entry point for clients
  • Controllers — receive HTTP requests, return responses

Functions:

  • Handle user input (clicks, data entry)
  • Display data to the user
  • Client-side validation (email format, required fields)
  • Routing, navigation

Example with Angular:

src/app/
  components/
    login/
      login.component.ts
      login.component.html
    dashboard/
      dashboard.component.ts
  services/
    auth.service.ts
    api.service.ts
  guards/
    auth.guard.ts

Presentation Layer only calls Application Layer through HTTP APIs, does not access the database directly.

APPLICATION & DOMAIN LAYER

Application Layer

Role: Orchestrates business logic flow.

  • Services — orchestrate business operations
  • Use Cases — handle specific tasks
  • DTOs — Data Transfer Objects between layers

Example with Java Spring Boot:

@Service
public class CourseService {
  @Autowired
  private CourseRepository repo;

  public CourseDTO getCourse(Long id) {
    Course c = repo.findById(id)
      .orElseThrow();
    return mapper.toDTO(c);
  }
}

Domain / Business Logic Layer

Role: Centralized processing of business rules.

  • Entities — business objects (User, Course, Order)
  • Business Rules — rules (price ≥ 0, enrollment ≤ max)
  • Value Objects — Email, Money, Address
  • Domain Events — business events
@Entity
public class Course {
  @Id @GeneratedValue
  private Long id;
  private String title;
  private BigDecimal price;

  public void enroll(User user) {
    if (students.size() >= maxCapacity)
      throw new FullException();
    students.add(user);
  }
}

DATA LAYER

Role: Manages the system's data — stores and retrieves from database or other sources.

Components:

  • Repositories — data access interface
  • DAO (Data Access Objects) — concrete implementation
  • ORM Mapping — Entity ↔ Table mapping (JPA/Hibernate)
  • Database Migrations — Flyway, Liquibase

Example Repository (Spring Data JPA):

public interface CourseRepository
    extends JpaRepository<Course, Long> {

  List<Course> findByCategory(String cat);

  @Query("SELECT c FROM Course c
    WHERE c.price <= :max")
  List<Course> findAffordable(BigDecimal max);
}

Each package corresponds to 1 layer — helping organize code clearly following layered architecture.

LAYERED ARCHITECTURE — ADVANTAGES & DISADVANTAGES

Advantages:

  • Easy maintenance — changing 1 layer does not affect other layers
  • Clear separation — each layer has its own responsibility (Separation of Concerns)
  • Easy to test — mock each layer for unit testing
  • Extensible — add layers or change implementation
  • Team collaboration — FE team works on Presentation, BE team works on Business + Data

Disadvantages:

  • Performance overhead — requests must pass through multiple layers
  • More complex — more layers = more boilerplate code
  • Hard to optimize — data flow must go through each layer
  • Tight coupling between layers — if not well designed
✨ MODERN TRENDS

Java Spring Boot + Angular is a classic example of Layered Architecture: Angular (Presentation) → Spring Controllers (Application) → Services (Domain) → JPA Repositories (Data).

MVC PATTERN — OVERVIEW

Model-View-Controller (MVC) is a pattern that separates the application into 3 independent components, helping to separate logic, interface, and control. This is the most popular variant of Layered Architecture for web apps. [Wikipedia]

3 Components:

  • Model — Data and business logic (Entity, Service, Repository)
  • View — User interface (HTML/CSS, Angular templates)
  • Controller — Orchestrates: receives requests from View, calls Model, returns results to View

Workflow:

User → Controller (receives request) → Model (processes data) → View (displays) → User

MVC Pattern — interaction flow between Model, View, Controller

MVC — ADVANTAGES & DISADVANTAGES

Advantages:

  • Separation of Concerns — clearly separates logic, interface, control
  • Parallel Development — FE and BE develop simultaneously
  • Reusable Models — Model shared across multiple Views
  • Testable — unit test Controller and Model separately
  • Framework support — Spring MVC, Angular, .NET MVC all built-in

Disadvantages:

  • Learning curve — need to understand the MVC flow well
  • Boilerplate code — many files for 1 feature (Entity, DTO, Service, Controller, Component, Template)
  • Controller bloat — without separating Service, Controller easily becomes a "God class"
  • Complex for simple UI — overhead for small applications

MICROSERVICES ARCHITECTURE — OVERVIEW

The application is developed as a collection of small, independent, and loosely coupled services. Each service is responsible for a specific business capability and can be developed, deployed, and scaled independently. [Martin Fowler]

Example: An e-commerce application consisting of: UserService, ProductService, OrderService, PaymentService, NotificationService — each service has its own database, deployed separately, and can be written in different languages.

Independence

Each service is an independent unit — develop, deploy, maintain separately

Bounded Context

Each service is responsible for 1 specific business function

Decentralized Data

Each service manages its own database — data isolation

APIs for Communication

Communicate via REST, gRPC, or messaging (Kafka)

20 MSc. Nguyen Viet Hung - CMC University

MICROSERVICES CHARACTERISTICS

CharacteristicDescription
IndependenceEach microservice is an independent unit that can be developed, deployed, and maintained separately
Bounded ContextEach service is responsible for 1 specific business function (e.g., user management, payment processing) and has its own domain
Decentralized DataEach service manages its own database, ensuring data isolation — no shared DB between services
APIs for CommunicationCommunicate via lightweight APIs: REST, gRPC, or messaging protocols (Kafka, RabbitMQ)
Polyglot DevelopmentEach service can use different languages/frameworks as needed (Java, Node.js, Python, Go)
ResilienceFailure in 1 service does not directly affect other services — graceful degradation
ScalabilityScale each service independently based on demand (e.g., PaymentService needs more scaling than ProfileService)
21 MSc. Nguyen Viet Hung - CMC University

MICROSERVICES — ADVANTAGES & DISADVANTAGES

Advantages:

  • Scalability — scale each service independently
  • Flexibility in Technology — use different tech stacks
  • Faster Development — small teams develop in parallel
  • Improved Fault Isolation — errors don't spread
  • Easier Maintenance — small codebase, easy to understand
  • Independent Deployment — deploy without system-wide downtime

Disadvantages:

  • Increased Complexity — managing many services
  • Communication Overhead — network calls between services
  • Data Consistency — hard to maintain consistency across services
  • Requires robust DevOps — CI/CD, monitoring, logging for each service
  • Complex testing — integration testing across many services
✨ MODERN TRENDS

Netflix operates 1000+ microservices, Uber uses the DOMA (Domain-Oriented Microservice Architecture) model to manage complexity. [Uber Engineering]

EVENT-DRIVEN ARCHITECTURE (EDA) — OVERVIEW

Event-driven architecture — the workflow is controlled by events. Focuses on producing, detecting, and reacting to events. Highly adaptable for asynchronous, distributed, and real-time systems. [Wikipedia]

Event Producer

Creates events when state changes (e.g., order placed, sensor triggered). Publishes event to Event Broker.

Event Broker

Central hub for managing events — receives from Producer, distributes to Consumer. E.g., Apache Kafka, RabbitMQ, Amazon SNS/SQS.

Event Consumer

Subscribes to event types of interest. Performs corresponding actions (send notification, process transaction).

Example: User places order → OrderService publishes event "OrderCreated" → PaymentService processes payment → NotificationService sends email → InventoryService updates stock.

23 MSc. Nguyen Viet Hung - CMC University

EVENT PRODUCERS & CONSUMERS

Producers:

  • Create events when an event or state change occurs
  • E.g., order placed, sensor triggered, user registered
  • Publish events to Event Broker
  • Don't need to know who will receive the event (decoupled)

Consumers:

  • Subscribe to event types of interest
  • Listen to (consume) events from Event Broker
  • Perform corresponding actions
  • E.g., send notification, process payment, update cache

Event Broker (Middleware):

Central hub for managing events, ensuring events are distributed to all subscribed consumers.

BrokerCharacteristics
Apache KafkaHigh throughput, durable, distributed log. Suitable for large data pipelines
RabbitMQFlexible routing, multiple protocols (AMQP). Suitable for task queues
Amazon SNS/SQSManaged service, easy to scale. Suitable for cloud-native
24 MSc. Nguyen Viet Hung - CMC University

EDA — ADVANTAGES & DISADVANTAGES

Advantages:

  • Asynchronous Communication — no need to wait for response
  • Loose Coupling — services are not directly dependent
  • Scalability — scale each consumer independently
  • Flexibility — adding new consumers doesn't affect the system
  • Real-Time Processing — process immediately when event occurs

Disadvantages:

  • Increased Complexity — managing event flows is complex
  • Difficult debugging — tracing asynchronous flows
  • Event Ordering — hard to guarantee event order
  • Requires robust middleware — needs stable Kafka/RabbitMQ
  • Eventual Consistency — data is not immediately consistent
✨ MODERN TRENDS

LinkedIn processes 7 million events/second via Apache Kafka. IoT, fintech, and e-commerce systems all use EDA for real-time processing. [LinkedIn Engineering]

SOFTWARE ARCHITECTURE EVOLUTION

Software architecture is not fixed — it evolves with the system. Many large organizations have gone through the following evolution:

1

Monolithic

Start simple, ship MVP fast. E.g., Shopify, Netflix in early stages

2

Modular Monolith

Divide monolith into clear modules (bounded contexts), preparing for service separation. E.g., Shopify currently

3

Microservices

Split modules into independent services when scaling is needed. E.g., Netflix, Uber, Amazon

4

Event-Driven + Microservices

Combine async messaging for real-time, loose coupling. E.g., LinkedIn, fintech

✨ MODERN TRENDS

Martin Fowler advises: "MonolithFirst" — start with a monolith, only transition to microservices when truly needed. Premature decomposition is more costly than a monolith. [Martin Fowler]

ARCHITECTURE SELECTION GUIDELINES

1

Small team (<5 people), MVP, tight deadline?

→ Monolithic — simple, fast, easy to debug

2

Enterprise web app, need clear structure?

→ Layered Architecture — separation of concerns, easy to maintain, suitable for Java Spring Boot + Angular

3

Need real-time, async, data pipeline?

→ Event-Driven — Kafka/RabbitMQ, loose coupling, real-time processing

4

Large system, multiple teams, need to scale individual parts?

→ Microservices — independent deployment, polyglot, fault isolation

✨ MODERN TRENDS

Many organizations start with Monolithic → Modular Monolith → Microservices (evolutionary architecture). You should not use microservices from the start if the team is small and doesn't fully understand the domain. [Martin Fowler]

CASE STUDY: NETFLIX'S ARCHITECTURE EVOLUTION

Development Phases:

YearArchitectureReason for Transition

The transition took 7 years — not overnight. [Netflix Tech Blog]

Lessons Learned:

  • Start monolithic when domain is not fully understood
  • Transition to microservices when there is a real need (scale, large team)
  • Migration is a long process, not a rewrite
  • Need DevOps maturity before transitioning (CI/CD, monitoring, logging)
  • Chaos Engineering (Chaos Monkey) to test fault tolerance
