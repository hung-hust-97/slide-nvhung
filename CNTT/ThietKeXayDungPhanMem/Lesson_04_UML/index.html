UML — TỔNG QUAN

UML (Unified Modeling Language) là ngôn ngữ đồ họa tiêu chuẩn để mô tả, trực quan hóa, xây dựng và tài liệu hóa các hệ thống hướng đối tượng. [Wikipedia]

3 loại mô hình hóa:

  • UC Modeling — yêu cầu chức năng (Use Case Diagrams)
  • Static Modeling — cấu trúc hệ thống (Class, Component, Package)
  • Dynamic Modeling — hành vi hệ thống (Sequence, Activity, State)

Công cụ vẽ UML:

  • draw.io — miễn phí, kéo thả, export PNG/SVG
  • PlantUML — code-based, version control trên Git
  • StarUML, Visual Paradigm — professional tools
  • Mermaid — viết trong Markdown

CƠ CHẾ MỞ RỘNG UML

UML cung cấp 3 cơ chế để mở rộng ngôn ngữ cho phù hợp với domain cụ thể:

Tagged Value

Mở rộng thuộc tính, thêm thông tin mới. Đặt trong ngoặc nhọn: {tag = value}. VD: {version = "2.0"}, {author = "Hung"}

Constraint

Điều kiện phải đúng — thêm quy tắc mới hoặc sửa đổi quy tắc hiện có. VD: {ordered}, {readonly}, {balance >= 0}

Stereotype

Định nghĩa building block mới từ UML element hiện có, tùy chỉnh theo domain. Đặt trong guillemets: «entity», «service», «controller»

VD trong Spring Boot: «entity» User, «repository» UserRepository, «service» UserService, «controller» UserController

CLASS DIAGRAM & OBJECT DIAGRAM

Class Diagram:

Biểu đồ cấu trúc thể hiện bản thiết kế hệ thống — các lớp, thuộc tính, phương thức và mối quan hệ.

  • Class: tên, attributes (-private, +public), methods
  • Association: quan hệ giữa classes (1:1, 1:N, M:N)
  • Inheritance: kế thừa (extends)
  • Interface: implements
  • Composition/Aggregation: chứa/thuộc về

Object Diagram:

Ảnh chụp hệ thống tại thời điểm cụ thể — hiển thị instances và trạng thái thực tế.

PACKAGE DIAGRAM

Minh họa tổ chức và dependencies giữa các packages trong hệ thống:

  • Tổ chức cấu trúc hệ thống một cách logic
  • Quản lý hệ thống lớn bằng cách nhóm các phần tử liên quan
  • Trực quan hóa dependencies → giảm coupling
  • Đại diện cho namespace hierarchies

DATA FLOW DIAGRAM (DFD)

Biểu diễn đồ họa cấp cao về luồng dữ liệu trong hệ thống: [Wikipedia]

  • Luồng dữ liệu giữa modules, components
  • Data storage/cached

Các cấp độ DFD:

  • Level 0 (Context Diagram): tổng quan hệ thống + external entities
  • Level 1: phân rã quy trình chính thành sub-processes
  • Level 2+: chi tiết hơn từng sub-process

Các bước tạo DFD:

  • Xác định Processes (chức năng chính)
  • Xác định Data Flows (dữ liệu di chuyển thế nào)
  • Xác định Data Stores (lưu trữ ở đâu)
  • Xác định External Entities (ai tương tác)

RELATIONSHIPS & CARDINALITY

Relationships (Mối quan hệ):

LoạiMô tảVD
1:1Một thực thể liên kết với đúng 1 thực thể khácUser ↔ Profile
1:NMột thực thể liên kết với nhiều thực thể khácCustomer → Orders
M:NNhiều ↔ Nhiều (cần bảng trung gian)Students ↔ Courses

Cardinality (Bản số):

Chỉ rõ số lượng instances của entity có thể/phải liên kết:

  • Relationship 1:N → 1 customer có thể có nhiều orders
  • Cardinality 1:N → 1 customer phải có ít nhất 1 order

Ký hiệu:

  • 1 — chính xác 1
  • 0..1 — 0 hoặc 1 (tùy chọn)
  • 1..* — 1 hoặc nhiều (bắt buộc)
  • 0..* hoặc * — 0 hoặc nhiều

NORMALIZATION: 1NF & 2NF

1NF (First Normal Form):

  • Mỗi cột chứa giá trị nguyên tử (không thể chia nhỏ)
  • Mỗi hàng là duy nhất (có primary key)
  • Mỗi cột chứa giá trị cùng kiểu

VD vi phạm 1NF:

student_idnamephones
1Hưng0901234567, 0912345678

❌ Cột phones chứa nhiều giá trị → tách thành bảng riêng

2NF (Second Normal Form):

  • Bảng phải ở 1NF
  • Mọi non-key attribute phải phụ thuộc toàn bộ primary key (loại bỏ partial dependency)

VD vi phạm 2NF:

student_idcourse_idstudent_namegrade
1CS101HưngA

❌ student_name chỉ phụ thuộc student_id, không phụ thuộc toàn bộ PK (student_id + course_id)

✅ Tách: Students(id, name) + Enrollments(student_id, course_id, grade)

24 ThS. Nguyễn Việt Hưng - Trường Đại học CMC

NORMALIZATION: 3NF & BCNF

3NF (Third Normal Form):

  • Bảng phải ở 2NF
  • Không có transitive dependency (non-key attributes chỉ phụ thuộc PK)

VD vi phạm 3NF:

emp_iddept_iddept_name
1D01IT

❌ dept_name phụ thuộc dept_id (không phải PK emp_id)

✅ Tách: Employees(emp_id, dept_id) + Departments(dept_id, dept_name)

BCNF (Boyce-Codd Normal Form):

  • Bảng phải ở 3NF
  • Mọi determinant phải là candidate key
  • Giải quyết trường hợp overlapping candidate keys

Tóm tắt Normalization:

NFLoại bỏ
1NFRepeating groups, non-atomic values
2NFPartial dependency
3NFTransitive dependency
BCNFOverlapping candidate keys

PHYSICAL DESIGN

Chuyển logical design thành physical schema cho DBMS cụ thể (MySQL, PostgreSQL).

Các bước:

  • Transform schema → tables, columns, data types
  • Select data types → VARCHAR, INT, BIGINT, DECIMAL, DATETIME
  • Define storage → tablespace, partitioning
  • Configure indexing → B-tree, Hash, Full-text
  • Implement relationships → FK constraints, cascading

KEYS & INDEXES

Index là đối tượng database tăng tốc truy vấn bằng cách tạo cấu trúc tra cứu nhanh.

Lợi ích:

  • Giảm Full Table Scans
  • Tăng tốc JOIN operations
  • Hỗ trợ sorting và grouping
  • Truy vấn range hiệu quả

Hạn chế:

  • Tốn storage (mỗi index = 1 cấu trúc dữ liệu)
  • Chậm INSERT/UPDATE/DELETE (phải cập nhật index)
  • Over-indexing → phản tác dụng

Khi nào tạo Index?

Nên IndexKhông nên
Cột WHERE thường xuyênBảng nhỏ (<1000 rows)
Cột JOINCột ít distinct values
Cột ORDER BYCột hay UPDATE
Foreign KeysCột TEXT/BLOB lớn

VD MySQL Index:

-- Single column index
CREATE INDEX idx_email ON users(email);

-- Composite index
CREATE INDEX idx_course_date
  ON enrollments(course_id, enrolled_at);

-- Unique index
CREATE UNIQUE INDEX idx_unique_email
  ON users(email);

DATABASE SECURITY & BACKUP

Database Security:

  • Protect Sensitive Info — bảo vệ dữ liệu cá nhân, tài chính
  • Compliance — tuân thủ GDPR, HIPAA
  • Prevent Data Loss — giảm rủi ro hỏng/xóa nhầm
  • Maintain Integrity — ngăn sửa đổi trái phép

Biện pháp bảo mật:

  • Authentication (user/password, certificates)
  • Authorization (GRANT/REVOKE, RBAC)
  • Encryption (TDE, SSL/TLS connections)
  • Audit logging (ai truy cập gì, khi nào)
  • Input validation (SQL injection prevention)

DATABASE INDEXES — CHI TIẾT

Loại index phổ biến:

LoạiMô tả
B-treeMặc định MySQL/PostgreSQL, balanced tree
HashEquality lookup nhanh, không range query
BitmapCột ít distinct values
Full-textSearch trong text
SpatialGeographic data
CompositeNhiều cột
UniqueĐảm bảo unique constraint
PartialIndex 1 phần data

Cú pháp MySQL:

-- Single column
CREATE INDEX idx_email ON users(email);

-- Composite (order matters!)
CREATE INDEX idx_status_date
  ON orders(status, created_at);

-- Unique
CREATE UNIQUE INDEX idx_username
  ON users(username);

-- Full-text
CREATE FULLTEXT INDEX idx_description
  ON products(description);

-- Drop
DROP INDEX idx_email ON users;

-- Show indexes
SHOW INDEX FROM users;

-- Explain query plan
EXPLAIN SELECT * FROM users
  WHERE email = 'test@cmc.vn';

SQL JOINS — TRUY VẤN ĐA BẢNG

Các loại JOIN:

JOINMô tả
INNER JOINChỉ rows match cả 2 bảng
LEFT JOINTất cả rows bảng trái + match bảng phải
RIGHT JOINTất cả rows bảng phải + match bảng trái
FULL OUTERTất cả rows cả 2 bảng (PostgreSQL)
CROSS JOINCartesian product
SELF JOINJoin với chính nó

VD INNER JOIN:

SELECT u.name, o.order_date, o.total
FROM users u
INNER JOIN orders o ON u.id = o.user_id
WHERE o.status = 'completed';

LEFT JOIN — User chưa có order:

SELECT u.name, COUNT(o.id) AS order_count
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.id, u.name
ORDER BY order_count DESC;

SELF JOIN — Cây phân cấp:

SELECT e.name AS employee,
  m.name AS manager
FROM employees e
LEFT JOIN employees m
  ON e.manager_id = m.id;

Multiple JOINs:

SELECT u.name, p.title, oi.qty
FROM users u
JOIN orders o ON u.id = o.user_id
JOIN order_items oi ON o.id = oi.order_id
JOIN products p ON oi.product_id = p.id
WHERE o.created_at > '2026-01-01';
