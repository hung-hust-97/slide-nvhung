3 MSc. Nguyen Viet Hung - CMC University

UML — OVERVIEW

UML (Unified Modeling Language) is a standard graphical language for describing, visualizing, constructing, and documenting object-oriented systems. [Wikipedia]

3 types of modeling:

  • UC Modeling — functional requirements (Use Case Diagrams)
  • Static Modeling — system structure (Class, Component, Package)
  • Dynamic Modeling — system behavior (Sequence, Activity, State)

UML drawing tools:

  • draw.io — free, drag & drop, export PNG/SVG
  • PlantUML — code-based, version control on Git
  • StarUML, Visual Paradigm — professional tools
  • Mermaid — write in Markdown

UML EXTENSION MECHANISMS

UML provides 3 mechanisms to extend the language to fit specific domains:

Tagged Value

Extend properties, add new information. Placed in curly braces: {tag = value}. E.g.: {version = "2.0"}, {author = "Hung"}

Constraint

Conditions that must be true — add new rules or modify existing rules. E.g.: {ordered}, {readonly}, {balance >= 0}

Stereotype

Define new building blocks from existing UML elements, customized for the domain. Placed in guillemets: «entity», «service», «controller»

E.g. in Spring Boot: «entity» User, «repository» UserRepository, «service» UserService, «controller» UserController

  • Composition/Aggregation: contains/belongs to

DATA FLOW DIAGRAM (DFD)

A high-level graphical representation of data flow in a system: [Wikipedia]

  • Data flow between modules, components
  • Data storage/cached

DFD levels:

  • Level 0 (Context Diagram): system overview + external entities
  • Level 1: decompose main process into sub-processes
  • Level 2+: more detail for each sub-process

Steps to create DFD:

  • Identify Processes (main functions)
  • Identify Data Flows (how data moves)
  • Identify Data Stores (where data is stored)
  • Identify External Entities (who interacts)

DFD Notation:

NotationMeaning

Two parallel linesData store

✨ MODERN TRENDS

DFD is not part of UML but is still very useful for system analysis. In the course project, combine DFD Level 0 with Use Case Diagram for a comprehensive view.

ENTITIES & ATTRIBUTES

Entity:

An object or concept in the system whose data is stored.

  • Represented by a rectangle
  • Named with singular nouns: User, Course, Order
  • Strong Entity: exists independently (has its own PK)
  • Weak Entity: depends on another entity

RELATIONSHIPS & CARDINALITY

Relationships:

TypeDescriptionE.g.
1:1One entity is linked to exactly 1 other entityUser ↔ Profile
1:NOne entity is linked to many other entitiesCustomer → Orders
M:NMany ↔ Many (requires junction table)Students ↔ Courses

Cardinality:

Specifies the number of instances of an entity that can/must be linked:

  • Relationship 1:N → 1 customer can have many orders
  • Cardinality 1:N → 1 customer must have at least 1 order

Notation:

  • 1 — exactly 1
  • 0..1 — 0 or 1 (optional)
  • 1..* — 1 or many (required)
  • 0..* or * — 0 or many

NORMALIZATION: 1NF & 2NF

1NF (First Normal Form):

  • Each column contains atomic values (cannot be further divided)
  • Each row is unique (has a primary key)
  • Each column contains values of the same type

E.g. 1NF violation:

student_idnamephones
1Hưng0901234567, 0912345678

❌ The phones column contains multiple values → separate into its own table

2NF (Second Normal Form):

  • Table must be in 1NF
  • All non-key attributes must depend on the entire primary key (eliminate partial dependency)

E.g. 2NF violation:

student_idcourse_idstudent_namegrade
1CS101HưngA

❌ student_name depends only on student_id, not on the entire PK (student_id + course_id)

✅ Split: Students(id, name) + Enrollments(student_id, course_id, grade)

24 MSc. Nguyen Viet Hung - CMC University

NORMALIZATION: 3NF & BCNF

3NF (Third Normal Form):

  • Table must be in 2NF
  • No transitive dependency (non-key attributes depend only on PK)

E.g. 3NF violation:

emp_iddept_iddept_name
1D01IT

❌ dept_name depends on dept_id (not PK emp_id)

✅ Split: Employees(emp_id, dept_id) + Departments(dept_id, dept_name)

BCNF (Boyce-Codd Normal Form):

  • Table must be in 3NF
  • Every determinant must be a candidate key
  • Resolves overlapping candidate keys cases

Normalization Summary:

NFEliminates
1NFRepeating groups, non-atomic values
2NFPartial dependency
3NFTransitive dependency
BCNFOverlapping candidate keys

PHYSICAL DESIGN

Transform logical design into a physical schema for a specific DBMS (MySQL, PostgreSQL).

Steps:

  • Transform schema → tables, columns, data types
  • Select data types → VARCHAR, INT, BIGINT, DECIMAL, DATETIME
  • Define storage → tablespace, partitioning
  • Configure indexing → B-tree, Hash, Full-text
  • Implement relationships → FK constraints, cascading

E.g.: MySQL Physical Design

CREATE TABLE users (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  email VARCHAR(100) NOT NULL UNIQUE,
  password VARCHAR(255) NOT NULL,
  full_name VARCHAR(100) NOT NULL,
  role ENUM('STUDENT','TEACHER','ADMIN')
    DEFAULT 'STUDENT',
  created_at DATETIME DEFAULT NOW(),
  INDEX idx_email (email),
  INDEX idx_role (role)
) ENGINE=InnoDB CHARSET=utf8mb4;

KEYS & INDEXES

An index is a database object that speeds up queries by creating a fast lookup structure.

Benefits:

  • Reduces Full Table Scans
  • Speeds up JOIN operations
  • Supports sorting and grouping
  • Efficient range queries

Limitations:

  • Consumes storage (each index = 1 data structure)
  • Slows INSERT/UPDATE/DELETE (must update index)
  • Over-indexing → counterproductive

When to create an Index?

Should IndexShould Not
Frequently used WHERE columnsSmall tables (<1000 rows)
JOIN columnsColumns with few distinct values
ORDER BY columnsFrequently UPDATEd columns
Foreign KeysLarge TEXT/BLOB columns

E.g. MySQL Index:

-- Single column index
CREATE INDEX idx_email ON users(email);

-- Composite index
CREATE INDEX idx_course_date
  ON enrollments(course_id, enrolled_at);

-- Unique index
CREATE UNIQUE INDEX idx_unique_email
  ON users(email);

DATABASE SECURITY & BACKUP

Database Security:

  • Protect Sensitive Info — protect personal and financial data
  • Compliance — comply with GDPR, HIPAA
  • Prevent Data Loss — reduce risk of corruption/accidental deletion
  • Maintain Integrity — prevent unauthorized modifications

Security measures:

  • Authentication (user/password, certificates)
  • Authorization (GRANT/REVOKE, RBAC)
  • Encryption (TDE, SSL/TLS connections)
  • Audit logging (who accessed what, when)
  • Input validation (SQL injection prevention)

Backup & Recovery:

StrategyDescription
Full BackupEntire DB — slow but complete
IncrementalOnly changes since last backup
DifferentialChanges since last full backup
Point-in-timeRestore to a specific point in time
✨ MODERN TRENDS

Cloud databases (AWS RDS, Azure SQL) provide automated backup + point-in-time recovery. In the course project, configure MySQL backup in Docker Compose.

USE CASE — INCLUDE & EXTEND

«include» — Mandatory:

The child UC is always called when the parent UC runs. Separates shared logic.

"Place order"  --include-->  "Authenticate user"
"Purchase"     --include-->  "Authenticate user"

// Both UCs require authentication
// → Separate into a shared UC

«extend» — Optional:

The extending UC only runs under certain conditions.

"Apply coupon"  --extend-->  "Place order"

// Coupon only runs when user has a code
// Not mandatory

Generalization (inheritance):

An actor or UC inherits from another actor/UC.

       User
      /    \
  Student  Teacher
              \
            Admin

// Admin inherits from Teacher
// Teacher inherits from User
// Can do everything User can

Full example:

Cardinality notation:

NotationMeaning

──◯┤Zero or one (0..1)
──┤├One and only one
──<One or many (1..*)
──◯<Zero or many (0..*)

Customer ──┤├────<── Order

DATABASE INDEXES — DETAILS

Common index types:

TypeDescription
B-treeDefault in MySQL/PostgreSQL, balanced tree
HashFast equality lookup, no range query
BitmapColumns with few distinct values
Full-textSearch within text
SpatialGeographic data
CompositeMultiple columns
UniqueEnsures unique constraint
PartialIndexes part of the data

MySQL syntax:

-- Single column
CREATE INDEX idx_email ON users(email);

-- Composite (order matters!)
CREATE INDEX idx_status_date
  ON orders(status, created_at);

-- Unique
CREATE UNIQUE INDEX idx_username
  ON users(username);

-- Full-text
CREATE FULLTEXT INDEX idx_description
  ON products(description);

-- Drop
DROP INDEX idx_email ON users;

-- Show indexes
SHOW INDEX FROM users;

-- Explain query plan
EXPLAIN SELECT * FROM users
  WHERE email = 'test@cmc.vn';

⚠️ Indexes slow down INSERT/UPDATE — only create for frequently searched columns.

SQL JOINS — MULTI-TABLE QUERIES

Types of JOIN:

JOINDescription
INNER JOINOnly rows matching both tables
LEFT JOINAll rows from left table + matching from right
RIGHT JOINAll rows from right table + matching from left
FULL OUTERAll rows from both tables (PostgreSQL)
CROSS JOINCartesian product
SELF JOINJoin with itself

E.g. INNER JOIN:

SELECT u.name, o.order_date, o.total
FROM users u
INNER JOIN orders o ON u.id = o.user_id
WHERE o.status = 'completed';

LEFT JOIN — Users without orders:

SELECT u.name, COUNT(o.id) AS order_count
FROM users u
LEFT JOIN orders o ON u.id = o.user_id
GROUP BY u.id, u.name
ORDER BY order_count DESC;

SELF JOIN — Hierarchy tree:

SELECT e.name AS employee,
  m.name AS manager
FROM employees e
LEFT JOIN employees m
  ON e.manager_id = m.id;

Multiple JOINs:

SELECT u.name, p.title, oi.qty
FROM users u
JOIN orders o ON u.id = o.user_id
JOIN order_items oi ON o.id = oi.order_id
JOIN products p ON oi.product_id = p.id
WHERE o.created_at > '2026-01-01';
