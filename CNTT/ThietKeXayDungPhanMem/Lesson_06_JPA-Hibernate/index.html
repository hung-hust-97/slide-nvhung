ORM LÀ GÌ?

ORM (Object-Relational Mapping) là kỹ thuật lập trình cho phép tương tác với database bằng objects thay vì viết SQL thô. [Wikipedia]

Cách ORM hoạt động:

OOP→Database
Class→Table
Object→Row
Attribute→Column
Relationship (1:N)→Foreign Key
Relationship (M:N)→Join Table

SQL Generation: ORM tự động tạo SQL queries từ method calls (save, update, delete, find).

VD: Không dùng ORM (raw SQL)

String sql = "INSERT INTO users "
  + "(email, name) VALUES (?, ?)";
PreparedStatement ps = conn.prepareStatement(sql);
ps.setString(1, "hung@cmc.edu.vn");
ps.setString(2, "Hưng");
ps.executeUpdate(); // 😩 nhiều boilerplate

VD: Dùng ORM (JPA)

User user = new User();
user.setEmail("hung@cmc.edu.vn");
user.setName("Hưng");
userRepository.save(user); // ✅ 1 dòng!

ORM phổ biến nhất: Hibernate (Java), Entity Framework (.NET), TypeORM/Prisma (Node.js), SQLAlchemy (Python).

ORM — ƯU & NHƯỢC ĐIỂM

Ưu điểm:

  • Năng suất cao — tập trung business logic, không viết SQL
  • Database independence — chuyển DB dễ dàng (MySQL → PostgreSQL)
  • Code dễ đọc — giảm boilerplate, dùng objects thay SQL strings
  • Validation tích hợp — tự động enforce constraints
  • Auto schema generation — tạo bảng từ class definitions
  • Giảm lỗi SQL — SQL tự động tạo, ít human error

Nhược điểm:

  • Performance overhead — query sinh ra có thể không tối ưu
  • Learning curve — cần hiểu ORM framework + quirks
  • Ít kiểm soát query — khó fine-tune so với raw SQL
  • Complex relationships — mapping M:N, inheritance phức tạp
  • Debugging khó — SQL auto-generated khó trace
  • N+1 Problem — truy vấn lặp khi load lazy relationships

JPA VS HIBERNATE

JPA (Java Persistence API):

Specification (đặc tả) — tập hợp interfaces và annotations để quản lý dữ liệu trong Java.

  • Không phải implementation — chỉ là "hợp đồng"
  • Cung cấp: EntityManager, EntityManagerFactory
  • Annotations: @Entity, @Id, @Column, @OneToMany...
  • Query language: JPQL (Java Persistence Query Language)

Hibernate:

Implementation phổ biến nhất của JPA — cung cấp thêm nhiều tính năng.

  • Caching (1st & 2nd level cache)
  • HQL (Hibernate Query Language)
  • Schema generation, migration
  • Lazy/Eager loading strategies

So sánh:

JPAHibernate
LoạiSpecificationImplementation
Vai tròĐịnh nghĩa APITriển khai API
QueryJPQLHQL + JPQL
CachingKhông có1st & 2nd level
VendorOracle (Java EE)Red Hat

Databases hỗ trợ:

MySQL, PostgreSQL, Oracle, SQLite, H2, MSSQL...

Trong Spring Boot: spring-boot-starter-data-jpa tự động cấu hình Hibernate làm JPA provider.

ENTITYMANAGER & PERSISTENCE CONTEXT

EntityManager là interface chính của JPA để tương tác với database. Quản lý Persistence Context — vùng nhớ chứa các entities được quản lý.

Các operations chính:

MethodMục đích
persist(entity)INSERT — entity mới
merge(entity)UPDATE — entity đã có
find(class, id)SELECT theo PK
remove(entity)DELETE
flush()Đồng bộ với DB
refresh(entity)Reload từ DB
detach(entity)Bỏ quản lý
clear()Xóa toàn bộ context

Entity Lifecycle States:

New / Transient

Vừa new, chưa được quản lý, chưa có ID

Managed / Persistent

Được quản lý bởi context, sync với DB

Detached

Từng được quản lý, giờ tách ra (sau commit)

Removed

Đánh dấu xóa, sẽ DELETE khi flush

VD chuyển đổi states:

User u = new User();        // New
em.persist(u);              // Managed
em.flush();                 // INSERT
em.detach(u);               // Detached
em.merge(u);                // Managed lại
em.remove(u);               // Removed

HIBERNATE CACHING

1st Level Cache (mặc định, bật sẵn):

  • Scope: trong 1 EntityManager / Session
  • Tự động cache mọi entity được load
  • Lần thứ 2 query cùng entity → lấy từ cache
  • Chỉ hợp lệ trong 1 transaction
// Trong cùng transaction
User u1 = userRepo.findById(1L).get();  // SELECT
User u2 = userRepo.findById(1L).get();  // Cache!
// u1 == u2 (cùng instance)

2nd Level Cache (cấu hình thêm):

  • Scope: toàn bộ application
  • Chia sẻ giữa các sessions
  • Cần provider: EhCache, Hazelcast, Redis

Cấu hình 2nd Level Cache:

# application.yml
spring:
  jpa:
    properties:
      hibernate:
        cache:
          use_second_level_cache: true
          region:
            factory_class: org.hibernate.cache
              .jcache.JCacheRegionFactory

# Entity
@Entity
@Cache(usage =
  CacheConcurrencyStrategy.READ_WRITE)
public class Course { ... }

// Query Cache
@Cacheable
@QueryHints({@QueryHint(
  name = "org.hibernate.cacheable",
  value = "true")})
List<Course> findByCategory(String cat);

Trong microservices, dùng Redis làm distributed 2nd level cache — chia sẻ cache giữa nhiều instances của cùng service.

INHERITANCE MAPPING

JPA hỗ trợ 3 chiến lược ánh xạ kế thừa từ class cha:

StrategyMô tả
SINGLE_TABLE1 bảng chung cho cả parent + children, có cột discriminator (mặc định)
JOINEDMỗi class 1 bảng, JOIN qua FK
TABLE_PER_CLASSMỗi concrete class 1 bảng riêng

Khuyến nghị: SINGLE_TABLE — performance tốt nhất, query đơn giản.

VD: SINGLE_TABLE

@Entity
@Inheritance(strategy =
  InheritanceType.SINGLE_TABLE)
@DiscriminatorColumn(name = "user_type")
public abstract class User {
  @Id @GeneratedValue
  protected Long id;
  protected String email;
}

@Entity
@DiscriminatorValue("STUDENT")
public class Student extends User {
  private String studentCode;
  private String major;
}

@Entity
@DiscriminatorValue("TEACHER")
public class Teacher extends User {
  private String department;
  private BigDecimal salary;
}

// Bảng users:
// id | email | user_type | student_code |
// major | department | salary

COMPOSITE KEY — KHÓA CHÍNH GHÉP

Khi PK gồm nhiều cột (VD: bảng trung gian), dùng @EmbeddedId hoặc @IdClass.

Cách 1: @EmbeddedId

@Embeddable
@Data
public class EnrollmentId implements Serializable {
  private Long studentId;
  private Long courseId;
}

@Entity
public class Enrollment {
  @EmbeddedId
  private EnrollmentId id;

  @ManyToOne
  @MapsId("studentId")
  private Student student;

  @ManyToOne
  @MapsId("courseId")
  private Course course;

  private LocalDate enrolledAt;
  private String grade;
}

Cách 2: @IdClass

@Data
public class EnrollmentId implements Serializable {
  private Long studentId;
  private Long courseId;
}

@Entity
@IdClass(EnrollmentId.class)
public class Enrollment {
  @Id
  private Long studentId;

  @Id
  private Long courseId;

  @ManyToOne
  @JoinColumn(name = "student_id",
    insertable = false, updatable = false)
  private Student student;

  @ManyToOne
  @JoinColumn(name = "course_id",
    insertable = false, updatable = false)
  private Course course;
}

@EmbeddedId được khuyến nghị hơn — type-safe, code clean hơn.

BEAN VALIDATION TRONG ENTITY

JPA tích hợp Bean Validation — validate entity trước khi persist vào DB.

VD: Entity với validation

@Entity
public class User {
  @Id @GeneratedValue
  private Long id;

  @NotBlank(message = "Email bắt buộc")
  @Email(message = "Email không hợp lệ")
  @Column(nullable = false, unique = true,
    length = 100)
  private String email;

  @NotBlank
  @Size(min = 8, max = 255,
    message = "Password 8-255 ký tự")
  private String password;

  @NotBlank
  @Size(max = 100)
  private String fullName;

  @Min(value = 0)
  @Max(value = 150)
  private Integer age;

  @Past
  private LocalDate birthDate;

  @Pattern(regexp = "^[0-9]{10}$")
  private String phoneNumber;
}

Custom Validator:

@Target({ElementType.FIELD})
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy =
  StrongPasswordValidator.class)
public @interface StrongPassword {
  String message() default
    "Password phải có chữ hoa, thường, số, ký tự đặc biệt";
  Class<?>[] groups() default {};
  Class<? extends Payload>[] payload()
    default {};
}

public class StrongPasswordValidator
    implements ConstraintValidator
      <StrongPassword, String> {

  @Override
  public boolean isValid(String value,
      ConstraintValidatorContext ctx) {
    if (value == null) return false;
    return value.matches(
      "^(?=.*[a-z])(?=.*[A-Z])" +
      "(?=.*\\d)(?=.*[@$!%*?&]).{8,}$");
  }
}

// Sử dụng
@StrongPassword
private String password;

N+1 PROBLEM & CÁCH GIẢI QUYẾT

Vấn đề N+1:

Khi load 1 list entities có lazy collection, Hibernate sinh ra 1 query cho list + N queries cho mỗi entity.

List<User> users = userRepo.findAll();
// 1 query: SELECT * FROM users

for (User u : users) {
  System.out.println(u.getOrders().size());
  // N queries: SELECT * FROM orders WHERE user_id = ?
}
// Tổng: 1 + N queries! 🐌

Với 100 users → 101 queries → app chậm.

Giải pháp:

1. JOIN FETCH:

@Query("SELECT DISTINCT u FROM User u " +
  "LEFT JOIN FETCH u.orders")
List<User> findAllWithOrders();
// 1 query duy nhất với JOIN ✅

2. @EntityGraph:

@EntityGraph(attributePaths = {"orders"})
@Query("SELECT u FROM User u")
List<User> findAllWithOrders();

3. Batch fetching:

@Entity
public class User {
  @OneToMany(mappedBy = "user")
  @BatchSize(size = 20)
  private List<Order> orders;
}
// Load 20 collections cùng lúc

DTO PROJECTION — TĂNG TỐC QUERY

Khi chỉ cần vài fields, không nên load toàn bộ Entity → dùng Projection để chỉ SELECT cột cần thiết.

1. Interface Projection:

public interface UserSummary {
  Long getId();
  String getEmail();
  String getFullName();
}

public interface UserRepository
    extends JpaRepository<User, Long> {
  List<UserSummary> findAllProjectedBy();
  // SQL: SELECT id, email, full_name FROM users
}

2. Class-based Projection:

@Data
@AllArgsConstructor
public class UserDTO {
  private Long id;
  private String email;
  private String fullName;
}

@Query("SELECT new com.example.UserDTO(" +
  "u.id, u.email, u.fullName) " +
  "FROM User u WHERE u.role = :role")
List<UserDTO> findDTOByRole(
  @Param("role") Role role);

Lợi ích:

  • Giảm data truyền tải
  • Không load lazy collections
  • Tăng tốc query đáng kể
  • Tránh lộ Entity ra ngoài

JPA SPECIFICATIONS — DYNAMIC QUERIES

Specifications cho phép tạo query động dựa trên điều kiện runtime — phù hợp cho search/filter forms phức tạp.

Setup:

public interface UserRepository
    extends JpaRepository<User, Long>,
      JpaSpecificationExecutor<User> {
}

Tạo Specifications:

public class UserSpec {
  public static Specification<User>
      hasRole(Role role) {
    return (root, query, cb) ->
      cb.equal(root.get("role"), role);
  }

  public static Specification<User>
      emailContains(String keyword) {
    return (root, query, cb) -> cb.like(
      root.get("email"), "%" + keyword + "%");
  }
}

Sử dụng:

@Service
public class UserService {

  public Page<User> search(
      String email, Role role,
      Pageable pageable) {

    Specification<User> spec = Specification
      .where(null);

    if (email != null) {
      spec = spec.and(
        UserSpec.emailContains(email));
    }
    if (role != null) {
      spec = spec.and(
        UserSpec.hasRole(role));
    }

    return userRepo.findAll(spec, pageable);
  }
}

// Controller
@GetMapping("/search")
public Page<User> search(
    @RequestParam(required = false) String email,
    @RequestParam(required = false) Role role,
    Pageable pageable) {
  return userService.search(email, role, pageable);
}

@TRANSACTIONAL — QUẢN LÝ TRANSACTIONS

@Transactional đảm bảo tính ACID — nhiều operations chạy như 1 đơn vị, hoặc tất cả thành công, hoặc rollback hết.

Propagation:

TypeMô tả
REQUIREDDùng tx hiện tại hoặc tạo mới (mặc định)
REQUIRES_NEWLuôn tạo tx mới
NESTEDTx con trong tx cha
SUPPORTSDùng tx nếu có, không thì không
NEVERThrow exception nếu có tx

Isolation Levels:

  • READ_UNCOMMITTED — dirty read
  • READ_COMMITTED — không dirty (mặc định MySQL InnoDB)
  • REPEATABLE_READ — không phantom read
  • SERIALIZABLE — strict, chậm nhất

VD:

@Service
public class OrderService {

  @Transactional
  public Order createOrder(OrderDTO dto) {
    // 3 operations - phải all-or-nothing
    Order order = orderRepo.save(new Order(dto));
    inventoryRepo.decreaseStock(
      dto.getProductId(), dto.getQty());
    paymentRepo.charge(
      dto.getUserId(), dto.getAmount());
    return order;
    // Nếu bất kỳ bước nào fail → rollback hết
  }

  @Transactional(readOnly = true)
  public List<Order> getAll() {
    return orderRepo.findAll();
    // readOnly = optimization
  }

  @Transactional(
    rollbackFor = Exception.class,
    timeout = 30,
    isolation = Isolation.READ_COMMITTED)
  public void riskyOperation() { }
}

CONNECTION POOL — HIKARICP

HikariCP là connection pool mặc định của Spring Boot — nhanh nhất, ổn định nhất hiện nay. [GitHub]

Tại sao cần connection pool?

  • Tạo connection mới rất tốn kém (~100ms)
  • Pool tái sử dụng connections → nhanh
  • Giới hạn số connection đồng thời
  • Tự động close connections idle

Cấu hình:

spring:
  datasource:
    hikari:
      maximum-pool-size: 10
      minimum-idle: 5
      idle-timeout: 300000
      max-lifetime: 1800000
      connection-timeout: 30000
      pool-name: MyAppPool

Tuning Pool Size:

Công thức từ HikariCP wiki:

connections = ((core_count * 2) + effective_spindle_count)

# 4 cores + SSD:
# = 4 * 2 + 1 = 9 connections

Monitoring:

  • activeConnections — đang sử dụng
  • idleConnections — sẵn sàng
  • totalConnections — tổng
  • threadsAwaitingConnection — đang chờ (cần tăng pool!)

⚠️ Pool quá lớn → tốn RAM. Pool quá nhỏ → request bị block.

OPTIMISTIC LOCKING — @VERSION

Khi nhiều users cùng update 1 record, Optimistic Locking giúp phát hiện xung đột — không khóa DB.

Cách hoạt động:

  • Mỗi entity có cột version
  • UPDATE check version cũ
  • Nếu version đã thay đổi → throw exception
  • App tự retry hoặc báo lỗi cho user

Setup:

@Entity
public class Course {
  @Id @GeneratedValue
  private Long id;
  private String title;
  private BigDecimal price;

  @Version
  private Long version;
}

Cách dùng:

@Service
public class CourseService {

  @Transactional
  public Course updatePrice(Long id,
      BigDecimal newPrice) {
    try {
      Course course = courseRepo.findById(id)
        .orElseThrow();
      course.setPrice(newPrice);
      return courseRepo.save(course);
      // SQL: UPDATE courses SET price=?,
      //   version = version + 1
      //   WHERE id=? AND version=?
    } catch (
        OptimisticLockException ex) {
      throw new ConflictException(
        "Course has been modified by " +
        "another user. Please reload.");
    }
  }
}

Pessimistic Locking (alternative):

@Lock(LockModeType.PESSIMISTIC_WRITE)
Course findById(Long id);
// SELECT ... FOR UPDATE

SOFT DELETE — XÓA MỀM

Soft Delete không thực sự xóa record, chỉ đánh dấu deleted=true. Lợi ích: khôi phục dữ liệu, audit, compliance.

Cách 1: @SQLDelete + @Where

@Entity
@SQLDelete(sql = "UPDATE users " +
  "SET deleted = true, " +
  "deleted_at = NOW() " +
  "WHERE id = ?")
@Where(clause = "deleted = false")
public class User {
  @Id @GeneratedValue
  private Long id;
  private String email;
  private boolean deleted = false;
  private LocalDateTime deletedAt;
}

// userRepo.delete(user)
// → UPDATE users SET deleted=true ...
// findAll() chỉ trả deleted=false

Cách 2: Manual

@Service
public class UserService {

  @Transactional
  public void softDelete(Long id) {
    User user = userRepo.findById(id)
      .orElseThrow();
    user.setDeleted(true);
    user.setDeletedAt(LocalDateTime.now());
    userRepo.save(user);
  }

  public List<User> findActive() {
    return userRepo.findByDeletedFalse();
  }

  // Khôi phục
  public void restore(Long id) {
    userRepo.findById(id).ifPresent(u -> {
      u.setDeleted(false);
      u.setDeletedAt(null);
      userRepo.save(u);
    });
  }
}

⚠️ Soft delete làm bảng phình to dần — cần job định kỳ purge dữ liệu cũ.

BULK OPERATIONS & BATCH PROCESSING

Vấn đề: Insert nhiều records

// 1000 INSERT queries riêng lẻ - chậm!
for (User u : users) {
  userRepo.save(u);
}

Giải pháp 1: Batch Insert

spring:
  jpa:
    properties:
      hibernate:
        jdbc:
          batch_size: 50
        order_inserts: true
        order_updates: true
@Transactional
public void saveAll(List<User> users) {
  for (int i = 0; i < users.size(); i++) {
    em.persist(users.get(i));
    if (i % 50 == 0) {
      em.flush();
      em.clear();  // Tránh OOM
    }
  }
}

Bulk UPDATE/DELETE:

@Modifying
@Query("UPDATE User u " +
  "SET u.active = false " +
  "WHERE u.lastLogin < :date")
int deactivateInactiveUsers(
  @Param("date") LocalDateTime date);

@Modifying
@Query("DELETE FROM User u " +
  "WHERE u.deleted = true " +
  "AND u.deletedAt < :cutoff")
int purgeOldDeleted(
  @Param("cutoff") LocalDateTime cutoff);

Bulk operations chạy 1 SQL duy nhất → nhanh hơn hàng trăm lần so với loop.

@Configuration

  basePackages = "com.example.main",
  entityManagerFactoryRef = "mainEMF",
  transactionManagerRef = "mainTM")
public class MainDbConfig {

Use Case phổ biến:

  • Read/Write splitting — write vào primary, read từ replica
  • Microservices — mỗi service có DB riêng
  • Legacy integration — kết nối DB cũ
  • Multi-tenancy — mỗi tenant 1 DB

Read/Write Splitting:

@Service
public class UserService {

  @Autowired
  @Qualifier("primaryEMF")
  private EntityManager writeEM;

  @Autowired
  @Qualifier("replicaEMF")
  private EntityManager readEM;

  @Transactional
  public User create(UserDTO dto) {
    return writeEM.merge(dto.toEntity());
  }

  @Transactional(readOnly = true)
  public List<User> getAll() {
    return readEM.createQuery(
      "FROM User", User.class)
      .getResultList();
  }
}

PERFORMANCE TUNING TIPS

Top 10 tips:

  1. Index cột WHERE, JOIN, ORDER BY
  2. LAZY loading cho collections
  3. JOIN FETCH tránh N+1
  4. Pagination cho list lớn
  5. DTO Projection chỉ load fields cần
  6. Batch operations insert/update hàng loạt
  7. 2nd Level Cache cho dữ liệu ít thay đổi
  8. Connection pool tuning (HikariCP)
  9. Read replicas cho query nặng
  10. Database denormalization nếu cần

Code smells cần tránh:

// ❌ N+1 queries
List<User> users = userRepo.findAll();
users.forEach(u -> {
  System.out.println(u.getOrders().size());
});

// ✅ JOIN FETCH
@Query("SELECT DISTINCT u FROM User u " +
  "LEFT JOIN FETCH u.orders")
List<User> findAllWithOrders();

// ❌ Save trong loop
for (Order o : orders) {
  orderRepo.save(o);  // 1000 INSERT
}

// ✅ Batch save
orderRepo.saveAll(orders);  // 1 batch INSERT

// ❌ Load full Entity khi chỉ cần count
List<User> users = userRepo.findAll();
int total = users.size();

// ✅ Count query
long total = userRepo.count();

BEST PRACTICES JPA & HIBERNATE

Nên làm:

  • LAZY mặc định cho collections (@OneToMany, @ManyToMany)
  • JOIN FETCH hoặc @EntityGraph để tránh N+1
  • DTO Projection khi chỉ cần vài fields
  • @Transactional ở Service layer (không Repository)
  • readOnly = true cho query-only methods
  • Pagination cho list lớn
  • Flyway/Liquibase cho production migrations
  • HikariCP với pool size phù hợp
  • spring.jpa.show-sql=false ở production

Tránh:

  • ❌ EAGER fetch cho collections → load thừa
  • ❌ ddl-auto=update ở production
  • ❌ findAll() không có pagination
  • ❌ Truy cập lazy collection ngoài transaction → LazyInitializationException
  • ❌ Return Entity trực tiếp từ Controller
  • ❌ save() trong loop → batch insert thay thế
  • ❌ CascadeType.ALL không cần thiết → khó kiểm soát
  • ❌ Nhiều bidirectional relationships → vòng lặp khi serialize
  • ❌ N+1 queries — kiểm tra log SQL khi dev
✨ XU HƯỚNG HIỆN ĐẠI

jOOQ và Spring Data JDBC là alternatives nhẹ hơn JPA cho các project cần kiểm soát SQL chặt hơn.
