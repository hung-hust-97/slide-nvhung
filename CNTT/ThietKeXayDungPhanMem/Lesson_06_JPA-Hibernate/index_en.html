WHAT IS ORM?

ORM (Object-Relational Mapping) is a programming technique that allows interaction with databases using objects instead of writing raw SQL. [Wikipedia]

How ORM works:

OOP→Database
Class→Table
Object→Row
Attribute→Column
Relationship (1:N)→Foreign Key
Relationship (M:N)→Join Table

SQL Generation: ORM automatically generates SQL queries from method calls (save, update, delete, find).

Example: Without ORM (raw SQL)

String sql = "INSERT INTO users "
  + "(email, name) VALUES (?, ?)";
PreparedStatement ps = conn.prepareStatement(sql);
ps.setString(1, "hung@cmc.edu.vn");
ps.setString(2, "Hưng");
ps.executeUpdate(); // 😩 lots of boilerplate

Example: Using ORM (JPA)

User user = new User();
user.setEmail("hung@cmc.edu.vn");
user.setName("Hưng");
userRepository.save(user); // ✅ 1 line!
✨ MODERN TRENDS

Most popular ORMs: Hibernate (Java), Entity Framework (.NET), TypeORM/Prisma (Node.js), SQLAlchemy (Python).

ORM — ADVANTAGES & DISADVANTAGES

Advantages:

  • High productivity — focus on business logic, no SQL writing
  • Database independence — easy DB switching (MySQL → PostgreSQL)
  • Readable code — less boilerplate, use objects instead of SQL strings
  • Built-in validation — automatically enforce constraints
  • Auto schema generation — create tables from class definitions
  • Fewer SQL errors — SQL auto-generated, less human error

Disadvantages:

  • Performance overhead — generated queries may not be optimal
  • Learning curve — need to understand ORM framework + quirks
  • Less query control — hard to fine-tune compared to raw SQL
  • Complex relationships — mapping M:N, inheritance is complex
  • Difficult debugging — auto-generated SQL hard to trace
  • N+1 Problem — repeated queries when loading lazy relationships

JPA VS HIBERNATE

JPA (Java Persistence API):

Specification — a set of interfaces and annotations for managing data in Java.

  • Not an implementation — just a "contract"
  • Provides: EntityManager, EntityManagerFactory
  • Annotations: @Entity, @Id, @Column, @OneToMany...
  • Query language: JPQL (Java Persistence Query Language)

Hibernate:

The most popular Implementation of JPA — provides many additional features.

  • Caching (1st & 2nd level cache)
  • HQL (Hibernate Query Language)
  • Schema generation, migration
  • Lazy/Eager loading strategies

Comparison:

JPAHibernate
TypeSpecificationImplementation
RoleDefine APIImplement API
QueryJPQLHQL + JPQL
CachingNone1st & 2nd level
VendorOracle (Java EE)Red Hat

Supported databases:

MySQL, PostgreSQL, Oracle, SQLite, H2, MSSQL...

In Spring Boot: spring-boot-starter-data-jpa automatically configures Hibernate as the JPA provider.

ENTITYMANAGER & PERSISTENCE CONTEXT

EntityManager is the main JPA interface for interacting with the database. It manages the Persistence Context — a memory area containing managed entities.

Main operations:

MethodPurpose
persist(entity)INSERT — new entity
merge(entity)UPDATE — existing entity
find(class, id)SELECT by PK
remove(entity)DELETE
flush()Synchronize with DB
refresh(entity)Reload from DB
detach(entity)Stop managing
clear()Clear entire context

Entity Lifecycle States:

New / Transient

Just created with new, not managed, no ID yet

Managed / Persistent

Managed by context, synced with DB

Detached

Was managed, now detached (after commit)

Removed

Marked for deletion, will be DELETEd on flush

Example state transitions:

User u = new User();        // New
em.persist(u);              // Managed
em.flush();                 // INSERT
em.detach(u);               // Detached
em.merge(u);                // Managed again
em.remove(u);               // Removed

HIBERNATE CACHING

1st Level Cache (default, always enabled):

  • Scope: within 1 EntityManager / Session
  • Automatically caches all loaded entities
  • Second query for same entity → retrieved from cache
  • Only valid within 1 transaction
// Within the same transaction
User u1 = userRepo.findById(1L).get();  // SELECT
User u2 = userRepo.findById(1L).get();  // Cache!
// u1 == u2 (same instance)

2nd Level Cache (additional configuration):

  • Scope: entire application
  • Shared across sessions
  • Requires provider: EhCache, Hazelcast, Redis

Configuring 2nd Level Cache:

# application.yml
spring:
  jpa:
    properties:
      hibernate:
        cache:
          use_second_level_cache: true
          region:
            factory_class: org.hibernate.cache
              .jcache.JCacheRegionFactory

# Entity
@Entity
@Cache(usage =
  CacheConcurrencyStrategy.READ_WRITE)
public class Course { ... }

// Query Cache
@Cacheable
@QueryHints({@QueryHint(
  name = "org.hibernate.cacheable",
  value = "true")})
List<Course> findByCategory(String cat);
✨ MODERN TRENDS

In microservices, use Redis as a distributed 2nd level cache — share cache across multiple instances of the same service.

TypeDescriptionDefault for
EAGERLoad immediately when querying main entity@ManyToOne, @OneToOne

REMOVEDelete parent → auto delete children

INHERITANCE MAPPING

JPA supports 3 strategies for mapping inheritance from parent classes:

StrategyDescription
SINGLE_TABLE1 shared table for parent + children, with discriminator column (default)
JOINED1 table per class, JOIN via FK
TABLE_PER_CLASS1 separate table per concrete class

Recommendation: SINGLE_TABLE — best performance, simple queries.

Example: SINGLE_TABLE

@Entity
@Inheritance(strategy =
  InheritanceType.SINGLE_TABLE)
@DiscriminatorColumn(name = "user_type")
public abstract class User {
  @Id @GeneratedValue
  protected Long id;
  protected String email;
}

@Entity
@DiscriminatorValue("STUDENT")
public class Student extends User {
  private String studentCode;
  private String major;
}

@Entity
@DiscriminatorValue("TEACHER")
public class Teacher extends User {
  private String department;
  private BigDecimal salary;
}

// users table:
// id | email | user_type | student_code |
// major | department | salary

COMPOSITE KEY — COMPOUND PRIMARY KEY

When PK consists of multiple columns (e.g., join tables), use @EmbeddedId or @IdClass.

Method 1: @EmbeddedId

@Embeddable
@Data
public class EnrollmentId implements Serializable {
  private Long studentId;
  private Long courseId;
}

@Entity
public class Enrollment {
  @EmbeddedId
  private EnrollmentId id;

  @ManyToOne
  @MapsId("studentId")
  private Student student;

  @ManyToOne
  @MapsId("courseId")
  private Course course;

  private LocalDate enrolledAt;
  private String grade;
}

Method 2: @IdClass

@Data
public class EnrollmentId implements Serializable {
  private Long studentId;
  private Long courseId;
}

@Entity
@IdClass(EnrollmentId.class)
public class Enrollment {
  @Id
  private Long studentId;

  @Id
  private Long courseId;

  @ManyToOne
  @JoinColumn(name = "student_id",
    insertable = false, updatable = false)
  private Student student;

  @ManyToOne
  @JoinColumn(name = "course_id",
    insertable = false, updatable = false)
  private Course course;
}

@EmbeddedId is recommended — type-safe, cleaner code.

BEAN VALIDATION IN ENTITY

JPA integrates Bean Validation — validate entities before persisting to DB.

Example: Entity with validation

@Entity
public class User {
  @Id @GeneratedValue
  private Long id;

  @NotBlank(message = "Email is required")
  @Email(message = "Email is invalid")
  @Column(nullable = false, unique = true,
    length = 100)
  private String email;

  @NotBlank
  @Size(min = 8, max = 255,
    message = "Password 8-255 characters")
  private String password;

  @NotBlank
  @Size(max = 100)
  private String fullName;

  @Min(value = 0)
  @Max(value = 150)
  private Integer age;

  @Past
  private LocalDate birthDate;

  @Pattern(regexp = "^[0-9]{10}$")
  private String phoneNumber;
}

Custom Validator:

@Target({ElementType.FIELD})
@Retention(RetentionPolicy.RUNTIME)
@Constraint(validatedBy =
  StrongPasswordValidator.class)
public @interface StrongPassword {
  String message() default
    "Password must contain uppercase, lowercase, digit, special character";
  Class<?>[] groups() default {};
  Class<? extends Payload>[] payload()
    default {};
}

public class StrongPasswordValidator
    implements ConstraintValidator
      <StrongPassword, String> {

  @Override
  public boolean isValid(String value,
      ConstraintValidatorContext ctx) {
    if (value == null) return false;
    return value.matches(
      "^(?=.*[a-z])(?=.*[A-Z])" +
      "(?=.*\\d)(?=.*[@$!%*?&]).{8,}$");
  }
}

// Usage
@StrongPassword
private String password;

N+1 PROBLEM & SOLUTIONS

The N+1 problem:

When loading a list of entities with lazy collections, Hibernate generates 1 query for the list + N queries for each entity.

List<User> users = userRepo.findAll();
// 1 query: SELECT * FROM users

for (User u : users) {
  System.out.println(u.getOrders().size());
  // N queries: SELECT * FROM orders WHERE user_id = ?
}
// Total: 1 + N queries! 🐌

With 100 users → 101 queries → slow app.

Solutions:

1. JOIN FETCH:

@Query("SELECT DISTINCT u FROM User u " +
  "LEFT JOIN FETCH u.orders")
List<User> findAllWithOrders();
// 1 single query with JOIN ✅

2. @EntityGraph:

@EntityGraph(attributePaths = {"orders"})
@Query("SELECT u FROM User u")
List<User> findAllWithOrders();

3. Batch fetching:

@Entity
public class User {
  @OneToMany(mappedBy = "user")
  @BatchSize(size = 20)
  private List<Order> orders;
}
// Loads 20 collections at once

DTO PROJECTION — SPEED UP QUERIES

When only a few fields are needed, don't load the entire Entity → use Projection to SELECT only required columns.

1. Interface Projection:

public interface UserSummary {
  Long getId();
  String getEmail();
  String getFullName();
}

public interface UserRepository
    extends JpaRepository<User, Long> {
  List<UserSummary> findAllProjectedBy();
  // SQL: SELECT id, email, full_name FROM users
}

2. Class-based Projection:

@Data
@AllArgsConstructor
public class UserDTO {
  private Long id;
  private String email;
  private String fullName;
}

@Query("SELECT new com.example.UserDTO(" +
  "u.id, u.email, u.fullName) " +
  "FROM User u WHERE u.role = :role")
List<UserDTO> findDTOByRole(
  @Param("role") Role role);

Benefits:

  • Reduce data transfer
  • No lazy collections loaded
  • Significantly faster queries
  • Avoid exposing Entity externally

JPA SPECIFICATIONS — DYNAMIC QUERIES

Specifications allow creating dynamic queries based on runtime conditions — suitable for complex search/filter forms.

Setup:

public interface UserRepository
    extends JpaRepository<User, Long>,
      JpaSpecificationExecutor<User> {
}

Creating Specifications:

public class UserSpec {
  public static Specification<User>
      hasRole(Role role) {
    return (root, query, cb) ->
      cb.equal(root.get("role"), role);
  }

  public static Specification<User>
      emailContains(String keyword) {
    return (root, query, cb) -> cb.like(
      root.get("email"), "%" + keyword + "%");
  }
}

Usage:

@Service
public class UserService {

  public Page<User> search(
      String email, Role role,
      Pageable pageable) {

    Specification<User> spec = Specification
      .where(null);

    if (email != null) {
      spec = spec.and(
        UserSpec.emailContains(email));
    }
    if (role != null) {
      spec = spec.and(
        UserSpec.hasRole(role));
    }

    return userRepo.findAll(spec, pageable);
  }
}

// Controller
@GetMapping("/search")
public Page<User> search(
    @RequestParam(required = false) String email,
    @RequestParam(required = false) Role role,
    Pageable pageable) {
  return userService.search(email, role, pageable);
}

@TRANSACTIONAL — TRANSACTION MANAGEMENT

@Transactional ensures ACID properties — multiple operations run as a single unit, either all succeed or all rollback.

Propagation:

TypeDescription
REQUIREDUse current tx or create new (default)
REQUIRES_NEWAlways create new tx
NESTEDChild tx within parent tx
SUPPORTSUse tx if available, otherwise none
NEVERThrow exception if tx exists

Isolation Levels:

  • READ_UNCOMMITTED — dirty read
  • READ_COMMITTED — no dirty read (MySQL InnoDB default)
  • REPEATABLE_READ — no phantom read
  • SERIALIZABLE — strict, slowest

Example:

@Service
public class OrderService {

  @Transactional
  public Order createOrder(OrderDTO dto) {
    // 3 operations - must be all-or-nothing
    Order order = orderRepo.save(new Order(dto));
    inventoryRepo.decreaseStock(
      dto.getProductId(), dto.getQty());
    paymentRepo.charge(
      dto.getUserId(), dto.getAmount());
    return order;
    // If any step fails → rollback all
  }

  @Transactional(readOnly = true)
  public List<Order> getAll() {
    return orderRepo.findAll();
    // readOnly = optimization
  }

  @Transactional(
    rollbackFor = Exception.class,
    timeout = 30,
    isolation = Isolation.READ_COMMITTED)
  public void riskyOperation() { }
}

CONNECTION POOL — HIKARICP

HikariCP is the default connection pool in Spring Boot — the fastest and most stable available today. [GitHub]

Why use a connection pool?

  • Creating a new connection is expensive (~100ms)
  • Pool reuses connections → faster
  • Limits concurrent connections
  • Automatically closes idle connections

Configuration:

spring:
  datasource:
    hikari:
      maximum-pool-size: 10
      minimum-idle: 5
      idle-timeout: 300000
      max-lifetime: 1800000
      connection-timeout: 30000
      pool-name: MyAppPool

Tuning Pool Size:

Formula from HikariCP wiki:

connections = ((core_count * 2) + effective_spindle_count)

# 4 cores + SSD:
# = 4 * 2 + 1 = 9 connections

Monitoring:

  • activeConnections — in use
  • idleConnections — available
  • totalConnections — total
  • threadsAwaitingConnection — waiting (need to increase pool!)

⚠️ Pool too large → wastes RAM. Pool too small → requests get blocked.

✨ MODERN TRENDS

Spring Boot Actuator /actuator/metrics/hikaricp.connections to monitor pool health in real-time.

OPTIMISTIC LOCKING — @VERSION

When multiple users update the same record simultaneously, Optimistic Locking detects conflicts — without locking the DB.

How it works:

  • Each entity has a version column
  • UPDATE checks the old version
  • If version has changed → throw exception
  • App retries or reports error to user

Setup:

@Entity
public class Course {
  @Id @GeneratedValue
  private Long id;
  private String title;
  private BigDecimal price;

  @Version
  private Long version;
}

Usage:

@Service
public class CourseService {

  @Transactional
  public Course updatePrice(Long id,
      BigDecimal newPrice) {
    try {
      Course course = courseRepo.findById(id)
        .orElseThrow();
      course.setPrice(newPrice);
      return courseRepo.save(course);
      // SQL: UPDATE courses SET price=?,
      //   version = version + 1
      //   WHERE id=? AND version=?
    } catch (
        OptimisticLockException ex) {
      throw new ConflictException(
        "Course has been modified by " +
        "another user. Please reload.");
    }
  }
}

Pessimistic Locking (alternative):

@Lock(LockModeType.PESSIMISTIC_WRITE)
Course findById(Long id);
// SELECT ... FOR UPDATE

SOFT DELETE

Soft Delete doesn't actually delete records, just marks them as deleted=true. Benefits: data recovery, audit, compliance.

Method 1: @SQLDelete + @Where

@Entity
@SQLDelete(sql = "UPDATE users " +
  "SET deleted = true, " +
  "deleted_at = NOW() " +
  "WHERE id = ?")
@Where(clause = "deleted = false")
public class User {
  @Id @GeneratedValue
  private Long id;
  private String email;
  private boolean deleted = false;
  private LocalDateTime deletedAt;
}

// userRepo.delete(user)
// → UPDATE users SET deleted=true ...
// findAll() only returns deleted=false

Method 2: Manual

@Service
public class UserService {

  @Transactional
  public void softDelete(Long id) {
    User user = userRepo.findById(id)
      .orElseThrow();
    user.setDeleted(true);
    user.setDeletedAt(LocalDateTime.now());
    userRepo.save(user);
  }

  public List<User> findActive() {
    return userRepo.findByDeletedFalse();
  }

  // Restore
  public void restore(Long id) {
    userRepo.findById(id).ifPresent(u -> {
      u.setDeleted(false);
      u.setDeletedAt(null);
      userRepo.save(u);
    });
  }
}

⚠️ Soft delete causes tables to grow over time — need periodic jobs to purge old data.

BULK OPERATIONS & BATCH PROCESSING

Problem: Inserting many records

// 1000 individual INSERT queries - slow!
for (User u : users) {
  userRepo.save(u);
}

Solution 1: Batch Insert

spring:
  jpa:
    properties:
      hibernate:
        jdbc:
          batch_size: 50
        order_inserts: true
        order_updates: true
@Transactional
public void saveAll(List<User> users) {
  for (int i = 0; i < users.size(); i++) {
    em.persist(users.get(i));
    if (i % 50 == 0) {
      em.flush();
      em.clear();  // Avoid OOM
    }
  }
}

Bulk UPDATE/DELETE:

@Modifying
@Query("UPDATE User u " +
  "SET u.active = false " +
  "WHERE u.lastLogin < :date")
int deactivateInactiveUsers(
  @Param("date") LocalDateTime date);

@Modifying
@Query("DELETE FROM User u " +
  "WHERE u.deleted = true " +
  "AND u.deletedAt < :cutoff")
int purgeOldDeleted(
  @Param("cutoff") LocalDateTime cutoff);

Bulk operations run a single SQL statement → hundreds of times faster than looping.

@Configuration

Common use cases:

  • Read/Write splitting — write to primary, read from replica
  • Microservices — each service has its own DB
  • Legacy integration — connect to old DB
  • Multi-tenancy — each tenant has a separate DB

Read/Write Splitting:

@Service
public class UserService {

  @Autowired
  @Qualifier("primaryEMF")
  private EntityManager writeEM;

  @Autowired
  @Qualifier("replicaEMF")
  private EntityManager readEM;

  @Transactional
  public User create(UserDTO dto) {
    return writeEM.merge(dto.toEntity());
  }

  @Transactional(readOnly = true)
  public List<User> getAll() {
    return readEM.createQuery(
      "FROM User", User.class)
      .getResultList();
  }
}

PERFORMANCE TUNING TIPS

Top 10 tips:

  1. Index WHERE, JOIN, ORDER BY columns
  2. LAZY loading for collections
  3. JOIN FETCH to avoid N+1
  4. Pagination for large lists
  5. DTO Projection load only needed fields
  6. Batch operations for bulk insert/update
  7. 2nd Level Cache for rarely changing data
  8. Connection pool tuning (HikariCP)
  9. Read replicas for heavy queries
  10. Database denormalization if needed

Code smells to avoid:

// ❌ N+1 queries
List<User> users = userRepo.findAll();
users.forEach(u -> {
  System.out.println(u.getOrders().size());
});

// ✅ JOIN FETCH
@Query("SELECT DISTINCT u FROM User u " +
  "LEFT JOIN FETCH u.orders")
List<User> findAllWithOrders();

// ❌ Save in loop
for (Order o : orders) {
  orderRepo.save(o);  // 1000 INSERT
}

// ✅ Batch save
orderRepo.saveAll(orders);  // 1 batch INSERT

// ❌ Load full Entity when only count needed
List<User> users = userRepo.findAll();
int total = users.size();

// ✅ Count query
long total = userRepo.count();

JPA & HIBERNATE BEST PRACTICES

Do:

  • LAZY by default for collections (@OneToMany, @ManyToMany)
  • JOIN FETCH or @EntityGraph to avoid N+1
  • DTO Projection when only a few fields are needed
  • @Transactional at Service layer (not Repository)
  • readOnly = true for query-only methods
  • Pagination for large lists
  • Flyway/Liquibase for production migrations
  • HikariCP with appropriate pool size
  • spring.jpa.show-sql=false in production

Don't:

  • ❌ EAGER fetch for collections → loads too much
  • ❌ ddl-auto=update in production
  • ❌ findAll() without pagination
  • ❌ Access lazy collection outside transaction → LazyInitializationException
  • ❌ Return Entity directly from Controller
  • ❌ save() in loop → use batch insert instead
  • ❌ Unnecessary CascadeType.ALL → hard to control
  • ❌ Many bidirectional relationships → circular loops when serializing
  • ❌ N+1 queries — check SQL log during development
✨ MODERN TRENDS

jOOQ and Spring Data JDBC are lighter alternatives to JPA for projects that need tighter SQL control.
